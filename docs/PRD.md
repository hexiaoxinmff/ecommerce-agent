## 2. 产品背景

### 2.1 项目来源

本项目是一个面向电商业务场景的智能数据分析系统（课程/科研项目交付物）。业务数据库为自建 SQLite 电商库，覆盖用户、商品、分类、订单、订单明细 5 张核心表，全部为规则化合成数据（固定随机种子，可复现）。

### 2.2 用户痛点

电商业务人员（运营、商品、管理层）每天都需要用数据做决策，但普遍存在以下问题：

- **不会写 SQL**：业务问题（"上个月华东区卖得最好的 5 个品类是什么"）无法直接查询数据库。
- **依赖数据/研发排期**：取数需要提需求、等待排期，时效性差，难以支撑快速复盘与日常监控。
- **口径不清**：同一指标（"销售额"）在不同人、不同查询工具中含义不一致，结果难以信任。
- **结果不透明**：市面 AI 查数工具只给结论不给过程，用户无法验证数字是否可信。

### 2.3 传统 SQL 分析存在的问题

传统基于 SQL 的分析流程（人工写 SQL 或 BI 固定报表）存在：

- **门槛高**：SQL 学习成本与业务人员无关，人才依赖严重。
- **固化**：BI 报表面向预设问题，新问题需要新报表，扩展成本高。
- **琐碎**：大量高频、重复的取数需求占用了数据分析人员的时间，使其无暇处理复杂分析。

### 2.4 Text2SQL 的价值

Text2SQL 将自然语言问题自动转换为 SQL 并执行，使业务人员能够**直接用自己的语言向数据提问**，绕过 SQL 门槛与取数排期，实现：

- 高频常规取数自助化；
- 问题到结果的即时响应；
- 统一口径（由系统在 Schema 注释与 Prompt 中固化业务语义）。

### 2.5 Agent 化之后解决什么问题

单纯的 Text2SQL 只能"生成一条 SQL 再执行"，存在三个致命短板：

1. **不可控**：模型直接生成的 SQL 可能语法错误、引用不存在的字段、甚至包含危险语句——"生成即执行"存在安全风险（公开反面案例：Vanna 训练数据投毒 → 恶意 SQL 直接执行，见 `tech-research.md`）。
2. **不可解释**：出错了无法定位是"理解错了、表选错了、还是 SQL 写错了"，结果不可信。
3. **不可评测**：没有中间产物，无法量化改进，无法沉淀失败案例。

Agent 化（LangGraph 控制式 Agent）将流程显式拆分为**问题理解 → Schema Linking → Few-shot 检索 → SQL 生成 → SQL 校验 → SQL 执行 → 结构化结果**的固定链路，每个环节可观测、可校验、可归因，使系统具备**可执行、可验证、可纠错、可评测**的完整闭环，并为后续修复、多轮、图表、结论等能力提供可扩展的状态机底座。

> 本项目不是：普通 AI 聊天机器人、普通 BI 后台、单纯 Text2SQL Demo、单纯 SQL 生成器。

## 3. 产品目标

### 3.1 核心目标

让用户用**自然语言**即可完成电商数据的查询与分析，获得可信任、可追溯的结果。

### 3.2 工程目标

系统必须具备五个基本属性（项目级硬性要求）：

| 属性 | 含义 |
|---|---|
| **可执行** | 对于属于当前数据域、且能够通过语义与安全校验的问题，系统沿固定链路生成并执行 SQL，得到结构化结果；对于无法可靠回答的问题，系统进行受控拒答而非编造结果 |
| **可验证** | 每一步（Schema 选择、SQL、执行结果）都可检视、可核对，结果可回溯到真实查询 |
| **可纠错** | 生成与执行失败可定位到具体环节，后续具备反馈驱动的修复闭环（Repair） |
| **可评测** | 具备独立评测体系，以执行准确率（EX）为核心指标，支持分场景、分难度量化 |
| **可追踪** | 全链路 Trace 记录每个节点的输入/输出，可回放、可归因、可沉淀 Bad Case |

> **可执行 ≠ 所有问题都必须强行生成 SQL。** 超出当前数据域、语义无法解析或安全校验不通过的问题，系统允许安全拒答并给出合理降级提示。

### 3.3 评测目标

与已冻结的 `evaluation-plan.md` 严格对齐，本文档不自行虚构任何指标数字：

- 阶段 1：**100 条高质量单轮问题**，覆盖最小 Text2SQL 基线链。
- 阶段 2：扩展到**约 200 条**，同时加入 Multi-turn 测试组。
- 最终：视质量与开发情况扩展至 **300～350 条**（不强制 350），测试集质量优先于数量。
- 核心指标：SQL 执行成功率（Exec Rate）、SQL 执行准确率（EX）、一次生成成功率（Pass@1）；工程指标：P50/P95 端到端响应时间、错误率、LLM 调用量、token 消耗。
- 具体目标数值：**待阶段 1 建立基线并实测后再定标**，实现前不设置假设性达标线。

## 4. 用户角色

本项目面向"非 SQL 能力"的业务决策人群，共计三类核心角色：

### 4.1 数据分析人员（提效用户）

具备数据分析能力但被高频取数占用时间，需要：

- 查询经营数据（代替手工写 SQL）；
- 快速生成分析结果；
- 查看生成的 SQL 以校验结果正确性（SQL 透明是硬需求）；
- 查看图表；
- 验证结果与其业务预期是否一致。

### 4.2 电商运营人员（主力用户）

面向选品、活动复盘、日常监控，需要：

- **销售分析**：销售额、销量、客单价等；
- **商品分析**：Top 商品、热销品类；
- **用户分析**：用户结构、复购、地区分布；
- **地区分析**：各省份/大区销售表现；
- **趋势分析**：日/周/月/季度销售趋势，帮助运营判断走势。

### 4.3 管理者（决策用户）

需要：

- 快速了解核心指标（本日/本月销售额、订单量）；
- 查看经营趋势；
- 发现异常（如某月销售额明显下降、某品类波动）。

> 角色数量克制，不扩展用户管理、权限体系（Out of Scope，见 `project-understanding.md`）。

## 6. 产品范围

按照已冻结的项目范围拆分，分为 P0 / P1 / P2 三级。

### P0 / 核心（产品交付基线）

| 范围项 | 说明 |
|---|---|
| SQLite 电商数据 | 自建电商业务库，合成数据，固定种子可复现 |
| Schema | 表结构、业务口径注释、Schema 元数据（基础 Schema 加载） |

| Text2SQL | 问题 → SQL 生成（最小基线链） |
| SQL 校验 | 独立安全校验层（语法 / 结构 / 安全策略） |
| SQL 执行 | 只读执行器（超时 / 行数限制 / 错误捕获） |
| 安全控制 | 只读、危险 SQL 拦截、Prompt Injection 防护等 |

| 范围项 | 说明 |
|---|---|
| Schema Linking 高级增强 | Dynamic Schema Clipping / 表列打分 / 更精细的 Schema 选择依据（I1） |
| Few-shot Retrieval 高级增强 | SQL Skeleton Similarity + Scenario-tagged 检索（I2） |
| SQL Repair | 失败反馈驱动的修复循环（有界，N 可配置） |
| SQL 展示 | 界面内展示生成 SQL 与校验/执行状态 |
| Trace | 全链路追踪、回放与 Bad Case 沉淀 |
| 多轮 | Multi-turn 追问、上下文继承（checkpointer） |
| 图表 | ECharts 图表生成（折线 / 柱状 / 饼 / Top-N） |
| 结论 | 结果分析 + 文字结论 + 结论与数据一致性校验 |
| 历史记录 | 历史问题 / SQL / 执行状态 / 结果摘要 / 时间记录；含「最近问题选择」能力 |

## 7. 阶段 1 最小基线

阶段 1 的唯一主线是以下 **7 阶段链路**，称为「最小 Text2SQL 基线链」（Minimal Text2SQL Baseline Pipeline）：

```text
Question
   ↓
Schema Linking        (基础环节：基础 Schema 加载 + 基础表/列匹配，输出 schema 子集)
   ↓
Few-shot Retrieval    (基础环节：基础示例检索)
   ↓
SQL Generation        (基于 schema 子集 + 示例生成 SQL)
   ↓
SQL Validation        (独立安全校验层：语法 / 结构 / 安全策略)
   ↓
SQL Execution         (只读、超时、行数上限)
   ↓
Structured Result     (表头 + 行 + 元信息 + Trace)
```

**阶段 1 基线由以下环节共同构成**：基础 Schema 加载 + 基础 Schema Linking + 基础 Few-shot Retrieval + SQL Generation + SQL Validation + SQL Execution + Structured Result。

> 阶段 1 基线环节为「基础 Schema Linking」「基础 Few-shot Retrieval」；**Dynamic Schema Clipping / 表列打分（I1）与 SQL Skeleton Similarity + Scenario-tagged 检索（I2）属于 P1 高级增强**，不混入"基线必须实现"的定义。

**阶段 1 明确不纳入核心基线**（属于后续扩展，不假装已实现）：

- SQL Repair（自动修复）
- Task Decomposition（任务拆解）
- Multi-turn（多轮）
- 完整图表生成
- 结论生成
- Multi-agent Consensus

> 阶段 1 交付重心 = 最小基线链正确运行 + 100 条单轮测试集评测 + 基础结果展示与 WebApp 基础框架。

## 8. 产品完整流程

### 8.1 最终产品形态（完整使用流程）

```text
用户输入问题
   ↓
问题理解（意图 / 主题 / 时间范围，后续含多轮上下文）
   ↓
Schema Linking
   ↓
Few-shot 检索
   ↓
SQL 生成
   ↓
SQL 安全校验 ──失败──> 后续阶段：异常处理 / Feedback Repair ※
   ↓ 通过
SQL 执行 ──失败──> 后续阶段：异常处理 / Feedback Repair ※
   ↓ 成功
结构化结果
   ↓
图表（ECharts 规格）
   ↓
分析结论（与查询结果一致性校验）
   ↓
用户继续追问（多轮）
```

> ※ **Feedback Repair 属于后续增强能力，阶段 1 不实现自动 Repair**；阶段 1 校验/执行失败时仅返回受控错误反馈（见第 12.3 节）。图中"异常处理 / 反馈修复"为最终产品形态。

### 8.2 当前开发阶段（阶段 1）

阶段 1 只实现高亮实线部分，其余为最终产品形态：

```text
用户输入问题
   ↓
问题理解 ────────────────（阶段 1：单轮为主）
   ↓
Schema Linking ─────────（阶段 1：基础 Schema Linking·P0；Dynamic Clipping 等高级增强为 P1）
   ↓
Few-shot 检索 ──────────（阶段 1：基础示例检索·P0；Skeleton Similarity 等高级增强为 P1）
   ↓
SQL 生成
   ↓
SQL 安全校验（独立安全校验层）──── 失败 → 受控错误反馈（阶段 1 无自动修复）
   ↓
SQL 执行
   ↓
结构化结果 + 基础展示
```

> 阶段 1 与最终产品形态**明确区分，不混为一谈**：SQL Repair、拆解、多轮、图表、结论均标记为后续扩展。

## 11. UI 设计原则

### 11.1 第一原则：数据优先

用户第一眼应该看到：**我的问题 / 我的数据 / 我的结论**，而不是装饰元素。页面视觉重心始终落在数据与分析结果上。

### 11.2 第二原则：AI 感要克制

产品是"数据分析工具"，不是聊天机器人。AI 元素只需体现智能能力（自然语言输入、链路可解释），**不要做成聊天机器人网页**。

### 11.3 第三原则：SQL 可追踪

用户应能看到完整链路：

```text
问题 → Schema → SQL → 执行状态 → 结果
```

但默认视觉层级为：**结果优先，SQL 次之，调试信息进一步下沉**（可展开查看，不默认堆在首屏）。

### 11.4 第四原则：图表专业

ECharts 图表必须：简洁、清晰、可比较、标签明确；不滥用 3D；不为了"炫"降低可读性。

## 12. 交互原则

### 12.1 输入问题

支持以下输入方式：

- 自然语言输入（主路径，P0）；
- 点击示例问题一键填入（P0）；
- 从最近问题中选择（归属 P1 历史记录能力）；
- 后续能力：对上一轮结果继续追问（多轮）。

### 12.2 执行状态

查询过程中必须让用户明确当前所处环节，禁止长时间空白等待：

```text
理解问题 → Schema 匹配 → 生成 SQL → SQL 校验 → 执行查询 → 生成结果
```

每个环节展示进行中状态（如"正在生成 SQL…"），可使用取消能力。

### 12.3 错误状态

必须覆盖以下错误场景并给出明确、友好的用户反馈：

| 错误类型 | 用户反馈 |
|---|---|
| SQL 语法错误 | "SQL 生成失败，原因：语法错误，建议换种问法" |
| SQL 安全拦截 | "该查询超出允许范围，已被安全系统拦截" |
| 数据库错误 | "查询执行失败，请稍后重试或调整问题" |
| LLM 调用失败 | "模型服务暂不可用，请稍后重试" |
| 查询超时 | "查询超时，建议缩小时间范围或简化问题" |
| 无数据 | "查询成功，但没有匹配的数据" |
| 问题无法回答 | "无法从当前数据回答该问题，建议改为……"（合理拒答，不编造） |

> 错误内部细节（表名、堆栈、Schema）只进 Trace/日志，不进用户响应（见第 14 节）。

## 14. 安全需求

与项目技术基线（`architecture-options.md` 第 8 节）保持一致，核心原则：

> **LLM 生成的 SQL ≠ 可以直接执行的 SQL。** 安全校验由确定性代码执行，不依赖 LLM 自觉。

| # | 安全项 | 要求 |
|---|---|---|
| 1 | 只读 SQL | 仅允许 SELECT 根节点；禁止 INSERT / UPDATE / DELETE / DROP / ALTER / TRUNCATE / CREATE / REPLACE 等 |
| 2 | 多语句禁止 | 仅允许单条 SQL（AST 级校验） |
| 3 | SQL AST 校验 | sqlglot 解析 + 语句类型白名单 + 表/列存在性校验 |
| 4 | SQLite read-only | 连接使用 `file:xxx.db?mode=ro` |
| 5 | query_only | 连接后执行 `PRAGMA query_only = ON` 双保险 |
| 6 | Prompt Injection 防护 | 问题文本仅作为查询意图注入；结构分离拼接；示例库入库必须过校验 + 人工审核 |
| 7 | 敏感字段保护 | 受限列不出现在 Schema 视图；禁止 SELECT * 命中后泄漏 |
| 8 | 行数限制 | 校验阶段强制注入 `LIMIT ≤ 500`（AST 改写） |
| 9 | 超时限制 | 查询超时（可配置，如 5s），独立看门狗中断并返回受控错误 |
| 10 | 错误信息脱敏 | 对外仅输出友好提示，内部细节只进 Trace/日志 |

## 15. 数据库产品语义

产品必须向用户与系统固化以下统一业务口径（四端一致：数据生成 / Schema / Prompt 示例 / 评测数据）。

### 15.1 金额字段语义

| 字段 | 语义 |
|---|---|
| `order_items.subtotal` | **单个订单明细行金额**（line-item amount），`= unit_price × quantity`，不含任何订单级调整 |
| `orders.total_amount` | **订单最终实付金额**（final paid order amount），含全部订单级调整 |

两者**可以不同**，差异来自可解释的业务因素，而不是"随机误差"：

- 商品折扣；
- 订单级优惠（满减/优惠券等，`discount_amount`）；
- 运费（`shipping_fee`）；
- 税费、退款等订单级调整。

### 15.2 口径公式

```text
total_amount = Σ(subtotal) − discount_amount + shipping_fee（+ 其他订单级调整）
```

> 全库已由 `scripts/init_db.py` 验证：该公式不一致订单数 = 0。禁止将两个字段的差异表述为数据误差。

### 15.3 统一销售统计口径

`cancelled`（取消）订单保留明细但实付为 0，**不计入任何"实际销售"类统计**：

- 商品销量、商品销售额、分类销售额等"实际销售"指标，**默认排除取消订单**（`WHERE o.status != 'cancelled'`）；
- 订单量、订单状态分布等结构类统计不受此限制；
- 该口径写入 SQL 生成 Prompt、示例库与评测 Gold SQL。

## 18. 评测与验收

与 `evaluation-plan.md` 完全对齐。

### 18.1 测试集分阶段策略

| 阶段 | 规模 | 说明 |
|---|---|---|
| 阶段 1 | **100 条高质量单轮问题** | 覆盖最小 Text2SQL 基线链，Easy/Medium/Hard/Extra 分级约 25/30/30/15 |
| 阶段 2 | **约 200 条 + Multi-turn** | 在 100 条基础扩展并加入多轮组 |
| 最终 | **300～350 条（可选，不强制 350）** | 视质量与开发情况决定，质量 > 数量 |

### 18.2 核心指标（阶段 1 启用）

- SQL 执行成功率（Exec Rate）；
- SQL 执行准确率（EX，pred 与 gold 执行结果一致）；
- 一次生成成功率（Pass@1）；
- 工程指标：P50/P95 响应时间、错误率、LLM 调用量、token 消耗。

### 18.3 Gold SQL 验收规范（强制）

Gold SQL 必须先经过以下 5 步才能进入正式测试集：

1. 人工审核业务语义（口径符合 `database-schema.md` 第 4、5 节）；
2. 确认 SQL 逻辑（表/字段/JOIN/聚合）；
3. 在真实项目数据库上实际执行；
4. 人工核对查询结果（数字、行数、边界值）；
5. 记录 `gold_result_hash` 后入集。

> **禁止**：将 AI 未经验证的生成结果直接当作 Gold SQL。

### 18.4 阶段 1 验收范围

- 最小 Text2SQL 基线链可运行、可评测；
- 100 条单轮测试集评测报告（分数卡 + 难度 × 场景交叉表 + Bad Case 清单）；
- 基础结果展示 + WebApp 基础框架（高端数据产品风格）；
- 安全校验层测试（危险 SQL 拦截样例可演示）；
- 阶段 1 量化达标线：**待 Baseline 实测后由项目负责人定标**；
- 阶段 1 验收范围**明确不包含**完整 ECharts 图表生成能力（图表属 P1）；首页图表区域仅按视觉容器/占位结构与结构化列表承载，不进入阶段 1 交付强制项。

## 19. 创新方向

以下为产品侧对应能力映射，最终是否作为答辩创新点以**实际实现与实验结果**为准，不夸大。

### 主要创新候选

| # | 创新方向 | 产品侧能力 |
|---|---|---|
| I1 | Schema Linking + 动态 Schema Clipping | 表/列打分裁剪，输出可检视的"选择依据"，失败可归因（页面展示 Schema 选择） |
| I2 | SQL Skeleton Similarity + Scenario-tagged Few-shot Retrieval | 无向量库依赖的确定性示例检索（提高生成准确率，可复现） |
| I3 | SQL Validation + Read-only Sandbox + Feedback Repair | 阶段拆分：**SQL Validation + Read-only Sandbox = 阶段 1 基础能力；Feedback Repair = 后续增强能力**。消融关系：Baseline → Validation + Read-only → Feedback Repair |
| I4 | Trace + Bad-case Optimization + Benchmark Loop | 全链路可追溯 + 失败自动入库反哺 Prompt/示例库（评测迭代闭环） |

> I3 不表示阶段 1 需一次性实现全部组成：其中 SQL Validation + Read-only Sandbox 属于阶段 1 基础能力，Feedback Repair 属于后续增强。

### Secondary / Optional（后续视实验决定）

- Task Decomposition（任务拆解）
- Conclusion / Data Consistency（结论一致性）
- Multi-candidate SQL（多候选）
- Multi-agent Consensus（多 Agent 共识）
- 更复杂的多轮策略

> 以上保留研发方向，**不在阶段 1 为主要"创新"而实现**。最终原则：只选择有本项目实验数据支撑的 3～4 项作为核心创新点。
