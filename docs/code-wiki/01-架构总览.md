# 01 · 架构总览

> 目标：用一页回答「系统由哪些层组成、一次请求在其中如何流动、Agent 状态机长什么样、代码目录如何映射到架构」。

## 1. 分层架构

系统是典型的**前后端分离 + 单进程后端**结构：

```text
┌──────────────────────────────────────────────────────────────────┐
│  表现层  Frontend（React 19 + Vite 8 + TypeScript + ECharts 6）    │
│  单页应用：首页 / 智能分析 / 数据集 / 历史 / 设置 / 登录             │
│  - AuthContext 管理登录态（4 态：authenticated / anonymous /       │
│    backend_unavailable / backend_error）                          │
│  - api/http.ts 统一注入 Bearer，401 自动清会话                     │
└───────────────────────────┬──────────────────────────────────────┘
                            │ HTTP / JSON（CORS: GET/POST/DELETE）
┌───────────────────────────▼──────────────────────────────────────┐
│  接口层  FastAPI（backend/app/main.py，12 个 router / 18 端点）      │
│  api/routes/*：参数校验（Pydantic）→ 调用服务层 → 状态码映射         │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│  编排层  LangGraph 有界状态图（backend/app/agent/）                 │
│  graph.py（构图）· nodes.py（节点+Trace包装）· state.py（状态）      │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│  领域层（每个子包 = 一个单一职责领域）                               │
│  schema/     Schema 内省 + 元数据 + Linking                        │
│  fewshot/    规则型示例检索（无向量库）                             │
│  sqlgen/     SQL 生成 + Prompt + 安全校验 + 条件性语义契约           │
│  sqlexec/    只读执行器（截断保护）                                 │
│  sqlrepair/  有限自修复（≤1 次）                                   │
│  sqlcheck/   作用域校验 + E3 Fan-out 检测（冻结）                   │
│  trace/      全链路事件记录                                        │
│  auth/       口令哈希 / 会话令牌 / 依赖注入                         │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│  基础设施层                                                        │
│  llm/    LLMProvider 抽象 + Mimo/Bailian/FallbackRouter           │
│  db/     sqlite.py（业务库只读）· appdb.py（应用库可写）             │
│  core/   config.py（环境变量统一入口）                              │
└──────────────────────────────────────────────────────────────────┘
```

**分层依赖铁律**：上层可依赖下层，下层**不得**反向依赖；`llm/` 是唯一允许 `import openai` 的地方；`db/sqlite.py` 不提供任何写方法。

## 2. 端到端数据流（以 `POST /api/agent/analyze` 为例）

```text
① 前端 AnalysisPage 收集 question
      └─ api/agent.ts → api/http.ts（注入 Authorization: Bearer <token>）
② 路由 api/routes/agent.py
      ├─ Depends(get_current_session) 校验 Bearer（无效→401）
      ├─ AgentRequest 校验（question 长度 1~500）
      └─ 调用 agent.graph.run_agent(question)
③ run_agent 取进程级缓存图 get_default_graph()，invoke({"question": q})
④ 图内 8 个节点依次执行（详见 §3），每节点：
      ├─ _wrap() 包一层：计耗时、写 TraceEvent、捕获异常不 raise
      └─ 只写自己负责的 State 字段
⑤ build_agent_result() 汇总终态 → AgentResult
⑥ 路由层落库：appdb.create_query_history(user_id, ...)（成功与失败都记）
⑦ 返回 AgentResponse（generated_sql / execution_result / trace / 计数 / 耗时）
```

## 3. LangGraph 有界状态机

### 3.1 图结构

```text
START
  → schema_link          # LLM 识别相关表/字段/理由/置信度 → 真实 Schema 复核
  → fewshot_retrieve     # 本地规则检索 Top-3 示例（不调 LLM）
  → sql_generate         # 拼 Prompt → LLM → 解析 JSON → 校验 → SQL
  → sql_safety           # sqlglot：单条 + 只读 SELECT/WITH + 写节点黑名单
      ├─ 不通过 → result ────────────────────────┐
      └─ 通过  → sql_execute                     │
            ├─ 成功              → result ───────┤
            ├─ Safety 拒绝        → result ───────┤（禁止 Repair）
            └─ 数据库执行错误     → sql_repair    │
                  ├─ repair 被拒 → result ───────┤
                  └─ repair 通过 → sql_execute_repaired → result
  result → END
```

### 3.2 有界性保证（核心设计约束）

| 约束 | 实现位置 | 说明 |
|---|---|---|
| `repair_count ≤ 1` | `nodes.route_after_execute` | 若 `repair_count >= 1` 直接走 `result`，不再进 `sql_repair` |
| `execute_count ≤ 2` | `sqlrepair/repairer.py` + 节点计数 | 首次执行 + 修复后执行，共 2 次 |
| Safety 拒绝不进 Repair | `route_after_execute` | `execute_error_kind == "safety"` → `result` |
| 失败后不再跑后续节点 | `nodes._wrap` | `state["success"] is False` 时后续节点记为 `skipped` |
| 绝不无限循环 | 全图无回边 | 所有边单向 + 条件边目标有限 |

### 3.3 状态定义（`agent/state.py`）

`AgentState` 是 `TypedDict(total=False)`，按用途分五组字段：

| 分组 | 字段 |
|---|---|
| 输入 | `question` |
| Schema Linking | `schema_tables` / `schema_columns` / `schema_reasons` / `schema_confidence` |
| Few-shot | `fewshot_examples` |
| SQL 生成/修复 | `generated_sql` / `original_sql` / `repaired_sql` / `repair_reason` / `repair_error` |
| 执行 | `execution_result` / `execution_error` |
| 计数 | `execute_count` / `repair_count` |
| 内部分支标志 | `sql_safety_ok` / `executed_ok` / `execute_error_kind` / `repair_ok` |
| 终态 | `success` / `final_error` |
| 错误分类（供 API 映射） | `http_status` / `error_type` |
| Trace | `trace`（`Annotated[list, operator.add]` 追加）/ `trace_final`（覆盖写） |

> `trace` 用 `operator.add` reducer：节点只需返回**单元素列表**即可自动追加，无需读改写。

## 4. 全链路 Trace 机制

- 8 个节点 = 固定 `TRACED_NODES` 序列（`trace/recorder.py`）。
- 每个 `TraceEvent` 三态：`success` / `error` / `skipped`，字段含 `sequence` / `node` / `status` / `duration_ms` / `message` / `input_summary` / `output_summary`。
- 未走到的条件分支节点（如未触发 Repair 时的 `sql_repair`）由 `result` 节点的 `finalize_events()` **补全为 `skipped`** 并给出可解释原因（如「未执行（无需修复）」），随后按固定顺序重编号。
- **异常不丢 Trace**：`_wrap` 捕获所有异常 → 记 `error` 事件 → 写 `success=False` / `error_type` / `http_status`，**不 raise**，保证 Trace 完整返回给前端。

## 6. 关键设计取舍（读懂代码意图的钥匙）

| 取舍 | 做法 | 位置 |
|---|---|---|
| **进程级缓存** | 图、Schema 目录、Few-shot 数据集各缓存一份，避免每请求重编译/重内省 | `graph.get_default_graph()` / `SchemaCatalog.get_cached()` / `dataset.get_dataset()`(lru_cache) |
| **不信任上游** | 执行器在执行前**再**做一次 Safety + Scope 校验（即使上游已校验） | `sqlexec/executor.execute()` |
| **条件性 Prompt 注入** | E8~E12 规则默认关闭，仅当 `SQLGEN_EXTRA_RULES` 命中且题目被确定性识别时才注入；未命中时 Prompt 与冻结基线**逐字节相同** | `sqlgen/prompt.py` + `semantic_contracts.py` / `entity_constraint.py` / `date_window.py` |
| **异常不 raise 出图** | 节点包装器吞异常转终态，保证 Trace 与 HTTP 语义 | `agent/nodes._wrap()` |
| **双库物理隔离** | 业务库只读、应用库可写，两套连接、两套路径 | `db/sqlite.py` vs `db/appdb.py` |
| **Provider 可插拔** | Protocol + 唯一工厂，上层零 `if provider ==` 分支 | `llm/provider.get_llm_provider()` |

## 7. 与「常见做法」的差异（避免误解代码）

- **不是自由 ReAct Agent**：没有「模型自主决定下一步」；节点与边是静态声明的，只有 2 处条件分支。
- **不是向量检索 Few-shot**：纯规则打分（关键词/表/列/场景加权 Jaccard），确定性、可解释、无外部依赖。
- **没有 ORM**：数据库访问是标准库 `sqlite3` + 手写参数化 SQL（SQLAlchemy 明确未使用）。
- **没有前端组件库**：自定义 CSS + 设计 Token（Tailwind / Ant Design 明确未使用）。
