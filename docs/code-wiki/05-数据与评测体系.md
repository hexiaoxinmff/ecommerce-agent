# 05 · 数据与评测体系

> 本篇回答两个问题：**系统的数据底座长什么样？怎么证明它答得对？**
> 数据底座是「两个物理隔离的 SQLite 库」；证明手段是「自建评测集 + 三道门禁 + EX 指标」。

---

## 1. 两个数据库：一个只读，一个可写

项目刻意把数据分成两个**独立文件**，权限模型完全相反：

| 库 | 文件 | 用途 | 访问权限 | 初始化脚本 |
|---|---|---|---|---|
| 业务库 | `db/ecommerce.db` | 被查询的电商数据 | **强制只读**（物理 + 会话双保险） | [`scripts/init_db.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/scripts/init_db.py) |
| 应用库 | `db/app.db` | 账号 / 会话 / 查询历史 | **可写**（唯一写入入口） | [`scripts/init_auth_db.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/scripts/init_auth_db.py) |

两个库的访问层也物理隔离：

- 业务库只读层：[sqlite.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/backend/app/db/sqlite.py)
- 应用库可写层：[appdb.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/backend/app/db/appdb.py)（注释明确声明「本层绝不打开、读取或修改 ecommerce.db」）

> ⚠️ `init_db.py` 会**删除并重建** `ecommerce.db`（`DB_PATH.unlink()`），而 `init_auth_db.py` 用 `CREATE TABLE IF NOT EXISTS` 保持**幂等**，重复执行不丢数据。二者的行为差异是有意为之。

## 2. 业务库 Schema（5 张核心表）

完整 DDL 定义在 [init_db.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/scripts/init_db.py#L24-L67) 的 `SCHEMA_DDL`：

```sql
users (id PK, username UNIQUE NOT NULL, email UNIQUE NOT NULL,
       region NOT NULL, register_date DATE NOT NULL,
       status IN ('active','inactive'))

categories (id PK, name UNIQUE NOT NULL, parent_id → categories.id)

products (id PK, name UNIQUE NOT NULL, category_id → categories.id,
          price REAL > 0, status IN ('on_sale','off_sale'))

orders (id PK, user_id → users.id, order_date DATE NOT NULL,
        status IN ('pending','paid','shipped','completed','cancelled'),
        region NOT NULL, discount_amount REAL ≥ 0, shipping_fee REAL ≥ 0,
        total_amount REAL ≥ 0)

order_items (id PK, order_id → orders.id, product_id → products.id,
             quantity INTEGER > 0, unit_price REAL > 0, subtotal REAL ≥ 0)
```

### 2.1 表规模与索引

`TABLE_NAMES` 常量（[sqlite.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/backend/app/db/sqlite.py)）与 README §9 一致：

| 表 | 行数（dev-2026-09-14） |
|---|---|
| `users` | 2000 |
| `categories` | 30 |
| `products` | 500 |
| `orders` | 10000 |
| `order_items` | 30457 |

索引（[init_db.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/scripts/init_db.py#L70-L77)）：

```sql
idx_orders_user_id / idx_orders_order_date / idx_orders_status
idx_order_items_order_id / idx_order_items_product_id
idx_products_category_id
```

### 2.2 业务口径（四端统一，禁止各写各的）

这三条口径是**评测正确性的前提**，后端 Prompt、Gold SQL、前端展示、文档必须一致（详见 [database-schema.md](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/docs/database-schema.md)）：

| 口径 | 定义 |
|---|---|
| `order_items.subtotal` | **明细行金额**（line-item amount），不含订单级优惠/运费 |
| `orders.total_amount` | **订单最终实付金额**，两者**不等价** |
| `cancelled` 订单 | 不计入「实际销售」类统计（销售额 / 销量 / 客单价），一律 `WHERE o.status != 'cancelled'`；订单量、状态分布等结构统计不受限 |

金额恒等式（`init_db.py` 的 `check_amount_semantics()` 会真实验证）：

```text
cancelled 订单:  total_amount = 0, discount = 0, shipping = 0
其他订单:        total_amount = SUM(order_items.subtotal) − discount_amount + shipping_fee
```

> 上述「差异」不是生成错误，而是**订单级优惠 / 运费**造成的可解释业务差异。评测集中 Gold SQL 必须遵守此口径。

### 2.3 双重只读保护

[executor.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/backend/app/sqlexec/executor.py) 与 [sqlite.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/backend/app/db/sqlite.py) 采用两层独立保护：

1. **文件级**：连接串 `file:db/ecommerce.db?mode=ro`（URI `mode=ro`），内核层拒绝写入；
2. **会话级**：连接建立后执行 `PRAGMA query_only = ON`，即使绕过 URI 也无法写入。

再加结果截断保护：`MAX_RESULT_ROWS = 500`，超出部分丢弃并标记 `truncated=true`，避免大表 OOM。

## 3. 应用库 Schema（3 表）

DDL 定义在 [appdb.py](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/backend/app/db/appdb.py#L34-L72) 的 `APP_SCHEMA_DDL`，`APP_TABLE_NAMES = ("auth_user", "auth_session", "query_history")`：

```sql
auth_user     (id PK, username UNIQUE, email UNIQUE, password_hash,
               created_at, is_active DEFAULT 1)

auth_session  (id PK, token_hash UNIQUE, user_id → auth_user.id,
               created_at, expires_at)

query_history (id PK, user_id → auth_user.id, session_id → auth_session.id,
               question, sql DEFAULT '', success INTEGER, error_message,
               result_summary, row_count, total_time_ms, created_at)
```

设计要点（务必遵守，源码注释已固化）：

- **只存哈希**：`password_hash` 接收 PBKDF2 哈希字符串，`token_hash` 接收 SHA-256 哈希字符串，本层**从不接收明文**；
- **参数化查询**：所有 SQL 一律占位符 + 参数元组，禁止拼接用户输入；
- **强制用户隔离**：`list_query_history` / `count_query_history` / `delete_query_history` 一律带 `WHERE user_id = ?`，`user_id` 取自服务端登录态，绝不信任前端参数；
- **时间统一**：`now_iso()` 输出 ISO 8601 UTC（秒级），如 `2026-09-25T12:34:56+00:00`。

### 3.1 数据访问函数（DAO）

| 函数 | 职责 | 关键约束 |
|---|---|---|
| `create_user(username, email, password_hash)` | 建账号，返回 id | UNIQUE 冲突抛 `IntegrityError` |
| `get_user_by_username / _by_email / _by_id` | 账号查询 | 参数化 |
| `create_session(user_id, token_hash, expires_at)` | 写会话，返回 id | 外键约束校验 user_id |
| `get_session(token_hash)` | 按 token 哈希查会话 | **不校验过期**（过期判定属登录态逻辑） |
| `delete_session(token_hash)` | 登出 | 同一事务内先把 `query_history.session_id` 置 NULL 再删，避免外键阻塞；异常整体回滚 |
| `create_query_history(...)` | 写历史，返回 id | `result_summary` 只存轻量摘要，禁止塞结果全集 |
| `list_query_history(user_id, limit, offset)` | 倒序分页列表 | 强制 `user_id` 隔离 |
| `count_query_history(user_id)` | 总数（供分页 total） | 强制 `user_id` |
| `delete_query_history(user_id, history_id)` | 删除一条 | 跨用户删除返回 `False` |

> 参见 [02-后端模块与关键代码.md](./02-后端模块与关键代码.md) 中 db 小节；认证哈希与 Bearer 逻辑见 auth 小节。

## 5. 评测口径：EX 如何判定

EX（Execution Accuracy）**不比较 SQL 文本，只比较执行结果**。唯一权威实现是 [`evaluation/normalization.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/evaluation/normalization.py) 的 `compare_results()`，规则对应 spec §D1~D9：

### 5.1 归一化与等价规则

| 规则 | 内容 | 对应函数 |
|---|---|---|
| D1 列数可比 | gold 有 n 列、pred 有 m 列，`n ≠ m` 直接判错 | `compare_results()` |
| 列名/alias 不敏感 | 只比较「每行的值集合」，列顺序任意 | `_row_as_sorted_tuple()` |
| 单元格归一化 | `None → ""`；`float → round(v, 6)`；金额 `currency → round(v, 2)` | `_normalize_cell()` |
| 行内排序 | 行内值按 `(类型名, repr)` 排序，消除列顺序差异 | `_row_as_sorted_tuple()` |
| D7 排名题并列容忍 | `order_sensitive=true` 时先集合验证、再按 Gold 顺序逐位验证；并列键内部顺序忽略 | `_rows_ordered_equal()` |
| D8 空结果 | 仅在 `expected_empty=true` 时 Gold 空才是合法基准，且 pred 也必须为空 | `compare_results()` |
| 金额容差 | 数值带 tolerance（金额取 `max(0.01, |v|×tolerance)`），其他精确 | `_cell_approx_equal()` |

### 5.2 安全阀设计

`compare_results()` 对**异常基准**主动判错而非放行：

- Gold 为空但**未**声明 `expected_empty` → 判错（基准异常）；
- Gold 非空但 pred 为空 → 判错。

这样避免「用错误 Gold 刷高分」。

> `gold_hash()`（同文件）是**另一件事**：它输出执行结果的规范 hash，**只用于 Gold Hash Gate 漂移检测，不用于判定预测正确**。EX 判定永远走 `compare_results()` 的值比较。

## 6. 指标定义

指标聚合的唯一实现是 [`evaluation/metrics.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/evaluation/metrics.py) 的 `aggregate()`：

| 指标 | 定义 | 计算式中 |
|---|---|---|
| **Exec Rate** | 最终 SQL 成功执行题数 / 总题数 | `exec_ok / total` |
| **EX** | 最终执行结果与 Gold 等价题数 / 总题数 | `ex / total` |
| **Conditional EX** | 仅对 `valid_model_runs`（provider 成功返回模型输出）计算 | `ex / valid` |
| **Pass@1（初始）** | `repair_count == 0` 且结果正确题数 / 总题数 | 一次成功 |
| **Final EX** | 含 repair 后的正确率（语义等于 EX） | `= ex` |
| **Repair Trigger Rate** | `repair_triggered / total` | 触发率 |
| **Repair Success Rate** | 触发 repair 中最终正确数 / 触发数 | 修复有效率 |
| **Latency** | all / success / failure 三组，各出 Avg / P50 / P95 / Min / Max | `_latency_stats()` |

聚合维度（`_group_stats()`）：`by_difficulty` / `by_scenario` / `by_operator` / `failure_stages` / `error_types`。

### 6.1 失败归因模型

单题结果 [`EvalCaseResult`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/evaluation/models.py#L9-L42) 记录：

- `failure_stage` ∈ `schema_link / fewshot / sql_generate / sql_safety / sql_execute / repair / result / provider / timeout`；
- `error_type`：异常类名或 `timeout`；
- `valid_model_run`：provider 是否成功返回（网络/超时错误为 `False`）。

**关键区分**：Provider 网络失败**不计入**模型能力失败（由 `valid_model_runs` / `provider_failures` / `timeouts` 单独统计），保证 EX 反映的是模型而非网络。

## 7. 评测 Runner：`scripts/run_eval.py`

入口 [`scripts/run_eval.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/scripts/run_eval.py)，直接调用真实 Agent（`app.agent.graph.run_agent`），不做任何 mock。

### 7.1 执行流程（顺序不可调换）

```text
① Benchmark Preflight（配置契约）      → 失败 exit 5
② Leakage Gate（Few-shot ↔ Benchmark） → 有泄漏 exit 4
③ Gold Hash Gate（100/100 重算比对）    → 漂移 exit 2
④ 选题筛选（--ids/--difficulty/--limit）
⑤ 记录 DB 文件 hash（前）
⑥ 串行评测（单题线程包超时，超时→error_type=timeout 继续）
⑦ 记录 DB 文件 hash（后）→ 前后不一致 exit 3
⑧ 汇总 metrics + 写报告 reports/eval/eval_{run_id}.json / .md
```

### 7.2 关键配置 `EvalConfig`

```python
EvalConfig(
    timeout_s=args.timeout,                 # 默认 60s
    max_retries=0 if args.no_retry else 1,  # Provider 网络错误最多重试 1 次
    enable_gold_hash_gate=not args.skip_hash_gate,
)
```

> Runner-level 重试与 Agent 内部 SQL Repair 是**两回事**，不要混用：前者处理网络抖动，后者处理 SQL 执行错误。

### 7.3 CLI 参数

```bash
python scripts/run_eval.py                       # 完整 100 条（串行）
python scripts/run_eval.py --limit 10            # 前 10 条
python scripts/run_eval.py --ids E-0001,E-0086   # 指定题号
python scripts/run_eval.py --difficulty hard     # 按难度
python scripts/run_eval.py --timeout 60          # 单题超时秒数
python scripts/run_eval.py --experiment e1_semantics_v1 \
                           --prompt-version SQLGENERATOR_PROMPT_V1.3 \
                           --fewshot-version FEWSHOT_V3     # 写入 meta
python scripts/run_eval.py --skip-hash-gate      # 调试用，跳过 Hash Gate
python scripts/run_eval.py --no-retry            # 关闭 Runner 重试
```

### 7.4 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 2 | Gold Hash Gate 失败（数据漂移） |
| 3 | 评测期间 DB 文件发生变化 |
| 4 | Leakage Gate 失败（Few-shot 泄漏） |
| 5 | Benchmark Preflight 失败（配置契约不满足） |

### 7.5 产物

- 报告：`reports/eval/eval_{run_id}.json` / `.md`，meta 含 `prompt_sha256` / `fewshot_sha256` / `dataset_sha256` / `db_table_counts` 等**可复现性字段**（`ev_report.build_meta()`）；
- Bad Case：写入 `data/eval/bad_cases/`（结构见该目录 README）。

## 8. 三道门禁（Gate）

这三个 Gate 是「评测结果可信」的工程保证，任何一道不过就**整体停止**，绝不出具「漂移/泄漏后的分数」。

### 8.1 Benchmark Preflight Contract

[`evaluation/benchmark_contract.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/evaluation/benchmark_contract.py) 的 `enforce_benchmark_contract()`，把「正式 benchmark」从环境约定升级为**强制实验契约**，6 条全满足才放行：

1. `LLM_PROVIDER == "bailian"`（禁止静默回落到 mimo）；
2. `BAILIAN_PRIMARY_MODEL` **显式非空**（只配 `BAILIAN_MODEL` 不认可）；
3. `BAILIAN_FALLBACK_MODELS` **为空**（正式评测不允许 fallback 池）；
4. `LLM_MODEL_LOCK` **显式为 true**；
5. 实际解析到的 provider 是**裸 `BailianProvider`**（`FreeTierFallbackRouter` 禁入）；
6. 实际 model **等于** `BAILIAN_PRIMARY_MODEL`。

> 设计动机：修复 `meta.model` 读错键（历史曾读 `MIMO_MODEL` 却实际调用 Bailian）导致的「产物与模型无绑定」问题。`meta.provider` / `meta.model` 一律取自本模块解析出的**实际值**，不读环境变量猜测。

### 8.2 Leakage Gate

[`scripts/check_benchmark_leakage.py`](file:///f:/基于%20Text2SQL%20的电商智能数据分析%20Agent/scripts/check_benchmark_leakage.py) 的 `check_leakage(fewshot_items, items)`：检查 Few-shot 示例集与 Benchmark 是否存在题目/结果泄漏。有泄漏 → exit 4，禁止评测。

### 8.3 Gold Hash Gate

`ev_runner.compute_gold_hash_gate(items, config)`：对 E-0001~E-0100 **全部重算** Gold 执行结果 hash 并与数据集内 `gold_result_hash` 比对，100/100 一致才通过。任一条漂移 → 抛 `GoldHashGateError` → exit 2。

> 它守的是「数据库 / Gold 没被悄悄改动」。DB 生成逻辑或表结构一旦变化，必须升级 `database_version` 并重新生成全部 `gold_result_hash`。
