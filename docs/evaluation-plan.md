> 日期：2026-09-14

---

## 1. 评测哲学

- **执行一致性优先**：判断"是否回答了问题"，以 pred SQL 与 gold SQL 的**执行结果一致**为准（Spider EX 思想），不以 SQL 文本是否相同为准。
- **分级可归因**：每个错误能定位到环节（schema linking / 生成 / 校验 / 执行），支持 Bad Case 沉淀与消融实验。
- **结论必须可验证（后续能力）**：AI 文字结论和图表必须能回溯到查询结果，评测"结论-数据一致率"。
- **工程指标同样硬性**：响应时间、错误率、LLM 调用量与 token 用量都要计量并写进报告。
- **数字来源纪律**：评测报告中的所有数字只允许三种来源——① 本项目实际实验；② 文献/公开 benchmark 报道（必须标注）；③ 明确标注的设计假设。**不允许把推测结果写成项目结果。**

## 2. 评测指标定义（指标全集）

> 指标全集在此定义；**分阶段启用**（阶段 1 只启用与最小基线链对应的指标，见第 3 节）。

### 2.1 Text2SQL 层

| 指标 | 定义 | 计算方式 |
|---|---|---|
| SQL 执行成功率（Exec Rate） | 生成的 SQL 通过校验且成功执行的比例 | 成功执行数 / 总题数 |
| SQL 执行准确率（EX） | pred SQL 结果与 gold SQL 结果一致（顺序敏感时规范排序后比较） | 一致题数 / 总题数（分难度分场景统计） |
| 一次生成成功率（Pass@1） | 第一次生成即正确（阶段 1 无修复循环，即"直接正确率"） | 一次正确数 / 总题数 |

> 修复成功率（Repair Success）、多轮理解准确率、拆解有效率等指标**在对应能力（Repair / Multi-turn / Decomposition）落地后启用**，阶段 1 不统计。

### 2.2 Agent 层（后续能力落地后启用）

| 指标 | 定义 |
|---|---|
| 自动修复成功率 | 首轮失败题中，经 ≤N 次修复后正确 |
| 多轮理解准确率 | 多轮会话中**每轮**问题最终 EX 的均值；另计"上下文依赖轮"（含指代/继承条件）的单独 EX |
| 复杂任务拆解有效率 | 触发拆解的题中，拆解后回答正确的比例（对比不拆解基线） |
| 平均修复轮次 / 超限率 | 每题平均进入 repair 的次数；达到上限仍失败的占比 |

### 2.3 结果质量层（结论生成落地后启用）

| 指标 | 定义 | 判定方法 |
|---|---|---|
| 结论-数据一致率 | 结论中的事实性陈述（数字、主体、趋势方向、Top 名单）与查询结果一致 | **双轨**：① 规则抽取——从结论与结果集中抽取数值/实体比对；② LLM-as-Judge——语义一致性评分（1-5 或 0/1），人工抽检 10% 校准 judge |
| 图-数据一致率 | 图表规格（x/y 轴、数值）与结果集一致 | 从 chart spec 反解数据与结果集比对 |
| 拒答合理性 | 无法回答时是否给出合理降级而非编造 | 人工抽检 |

### 2.4 工程层（阶段 1 即启用）

- 平均端到端响应时间（P50/P95，按难度分层）；
- 环节耗时分解（LLM 调用次数/题、token 消耗/题）；
- 系统错误率（非业务性 5xx/超时）；
- 查询超时/行数限制触发率（安全层有效性）。

## 3. 测试集分阶段策略（最终决策）

### 阶段 1（当前）：100 条高质量单轮问题

- 全部以 **single-turn Text2SQL** 为主，目标：验证**最小 Text2SQL 基线链**（7 阶段）。
- 分级建议（沿用 Spider 难度分级思想）：Easy ~25% / Medium ~30% / Hard ~30% / Extra ~15%。
- 覆盖测试集业务场景（销售/商品/用户/订单/地区/趋势等高价值场景优先）。
- **阶段 1 不强行加入大量多轮问题**（多轮属于后续能力）。

### 阶段 2：扩展到约 200 条

- 在 100 条基础上扩展至 **200 条左右**；
- **同时开始加入 multi-turn 测试组**（对应多轮能力落地）。

### 最终阶段：视质量与实际开发情况决定 300～350 条

- 目标是 **300～350 条左右**，**不是强制必须达到 350**；
- 是否继续扩展取决于：实际开发进度、Bad Case 沉淀质量、结论相关能力落地情况。

> **核心原则：测试集质量 > 测试集数量。** Gold SQL 不达标，宁可少放、不放。

## 4. 难度分级与条目结构

### 4.1 难度分级（对齐 Spider 分级，按 SQL 结构复杂度）

| 级别 | 结构特征 | 示例（电商） |
|---|---|---|
| Easy | 单表、无 JOIN、简单聚合/过滤 | "2025 年 6 月订单总数是多少？" |
| Medium | 单表多条件 / 分组聚合 / 排序取 Top | "各订单状态分别有多少单？" |
| Hard | 多表 JOIN / 子查询 / 窗口函数 / 占比率类 | "复购 3 次以上的用户占活跃用户比例？" |
| Extra | 多表嵌套 / 口径权衡 / 同比环比 / 多步骤 | "2025 年各季度 GMV 环比增长率及贡献 Top3 品类？" |
| 多轮（阶段 2 起） | 依赖上文：指代、继承、切换维度、改条件 | "看下广东的。" → "再按月拆开" → "只算手机" |

### 4.2 测试集条目结构（JSON）

```json
{
  "id": "E-0012",
  "stage": 1,
  "difficulty": "hard",
  "scenario": "user_analysis",       // 业务场景标签
  "operators": ["join", "groupby", "ratio"],  // SQL 特征标签（供误差分析）
  "question": "复购 3 次以上的用户占活跃用户的比例是多少？",
  "gold_sql": "SELECT ...",
  "gold_result_hash": "sha256(...)", // 防 gold 漂移
  "answer_slots": {"ratio": {"tolerance": 0.01}}, // 结论核对模板（后续能力用）
  "multi_turn": null                  // 阶段 2 起：多轮条目引用会话 id + 轮次
}
```

## 5. Gold SQL 生产规范（强制）

**不能直接把 AI 自动生成结果当作 Gold SQL** 进入正式测试集。

每个 Gold SQL 至少经过以下 5 个步骤：

1. **人工审核业务语义**：Gold 要回答的问题口径是否符合项目业务口径（如金额字段语义，见 `architecture-options.md` 第 7 节）；
2. **确认 SQL 逻辑**：表/字段/JOIN/聚合逻辑经人工确认无误；
3. **在真实项目数据库上实际执行**；
4. **确认查询结果符合预期**（人工核对结果数字、行数、边界值）；
5. **再进入正式评测集**（同时记录 gold_result_hash）。

> 禁止：AI 生成 Gold SQL → 不验证 → 直接入集。

## 6. Benchmark 初步方案

### 6.1 主 Benchmark

- 名称暂定：`ECO-SQL-Bench`（电商 Text2SQL 自建评测集 + 评测器）；
- 输入：测试集 JSON + 业务库（开发阶段规模）+ 系统配置；
- 输出：按已启用指标输出分数卡，**按难度 × 场景二维交叉表**输出；
- 可复现性：固定随机种子、固定模型温度、记录运行时模型版本/API 快照、锁定依赖版本；评测脚本一键重跑。

### 6.2 消融实验（对应后续能力与创新候选的验证）

| 实验 | 对照 | 启用阶段 | 对应创新候选 |
|---|---|---|---|
| E1 Schema Linking | 全量 schema vs 裁剪 schema | 阶段 1 起 | I1 |
| E2 Few-shot 检索 | 无示例 vs 随机示例 vs 骨架检索示例 | 阶段 1 起 | I2 |
| E3 Repair 循环 | 关修复 vs 开修复（N=3） | Repair 落地后 | I3 |
| E4 任务拆解 | 复杂题直出 vs 拆解 | 拆解落地后 | Secondary |
| E5 结论一致性校验器 | 有/无一致性校验 | 结论生成落地后 | Secondary |
| E6 多轮上下文 | 无历史 vs 指代消解开 | 多轮落地后 | Secondary |
| E7（可选）共识/多候选 | 单生成 vs 多候选投票 | 视需要 | Secondary |

> 阶段 1 只跑 E1 / E2（对应最小基线链的两个主创新点）。

### 6.3 回归评测

- 任何 Agent 逻辑/prompt 变更后跑**快速回归集**（阶段 1 先以 100 条全集为主，阶段 2 可划分更小的回归子集），分数劣化需说明原因。
- Bad Case 库：评测失败条目自动入库（问题、pred SQL、错误环节、gold、Trace），每轮迭代优先复测。

## 7. 创新点最终分级（最终决策）

### 7.1 明确不算创新的（技术选型，不写入创新）

FastAPI、LangGraph、React、ECharts、SQLite、调用 Mimo V2.5 Pro API——这些是选型，不是创新点。

### 7.2 主要创新候选（I1～I4，当前项目最主要创新方向）

| # | 创新点 | 性质 | 验证实验 |
|---|---|---|---|
| I1 | **Schema Linking + 动态 Schema Clipping**：表/列打分裁剪，输出可检视的"选择依据"，失败可归因 | 工程/方法强化 | E1 |
| I2 | **SQL Skeleton Similarity + Scenario-tagged Few-shot Retrieval**（无向量库依赖，确定性可复现） | 方法强化 | E2 |
| I3 | **SQL Validation + Read-only Sandbox + Feedback Repair** 闭环：独立安全校验层 + 只读执行 + 反馈驱动修复 | 工程闭环 | E1/E3 |
| I4 | **Trace + Bad-case Optimization + Benchmark Loop**：全链路可追溯 + 失败自动入库反哺 prompt/示例库 | 工程方法 | 全部实验的基础 |

### 7.3 Secondary / Optional（当前不承诺为核心创新）

- Task Decomposition（任务拆解）
- Conclusion / Data Consistency（结论一致性）
- Multi-candidate SQL（多候选）
- Multi-agent Consensus（多 Agent 共识）
- 更复杂的多轮策略

> 以上保留研发方向，但**不在阶段 1 为了"创新"而实现**。

### 7.4 最终原则

最终答辩只选择 **真正完成并有本项目实验数据支持的 3～4 项** 作为核心创新点，其余作为实现细节。

## 8. 评测执行流程（阶段 2 起实现）

1. `scripts/init_db.py` 重建业务库（开发阶段规模，保证评测环境一致）；
2. `evaluation/runner.py` 逐条跑测试集（记录 Trace）；
3. `evaluation/metrics.py` 计算已启用指标 + 交叉表；
4. `evaluation/report.py` 生成 Markdown/HTML 报告 + Bad Case 清单；
5. CI 化：pytest 针对核心节点的单元测试随开发跑，全量评测人工触发。
