## 1. 项目一句话定位

构建一个**以 Text2SQL 为核心、面向电商业务数据**的智能数据分析 Agent：

用户用自然语言提问，系统自动完成「问题理解 → Schema 理解/链接 → Few-shot → SQL 生成 → SQL 校验 → SQL 执行 → 结构化结果 → 后续分析（修复/结论/可视化/多轮）」的完整闭环。

**项目不是**：普通聊天机器人、单纯的 Text2SQL Demo、单纯的 LLM 调用项目、单纯的 BI 可视化工具。

**项目是**：

> **可执行、可验证、可纠错、可评测**的电商智能数据分析 Agent。

核心价值链路：

```
自然语言问题 → Schema 理解/链接 → Few-shot → SQL 生成 → SQL 校验 → SQL 执行 → 结构化结果 → 后续分析
```

并逐步扩展到修复、多轮、可视化和评测（详见 `architecture-options.md`）。

---

## 2. 我们到底在做什么：与普通 Text2SQL 的本质区别

| 维度 | 普通 Text2SQL 工具 | 本项目 |
|---|---|---|
| 输入 | 自然语言问题 | 自然语言问题 + 多轮对话上下文（后续能力） |
| 中间产物 | 一条 SQL | 完整可追溯链路（问题理解、表/字段选择依据、参考示例、SQL、校验结果、执行结果） |
| 输出 | SQL 文本 / 裸表格 | SQL + **结构化结果**，后续扩展至分析结论 + 可视化图表 + 数据依据 |
| 出错行为 | 直接报错或给错结果 | 校验 → 执行 → **自动修复循环**（后续能力）→ 仍失败则降级提示 |
| 复杂问题 | 依赖单条 SQL 硬解 | 允许**任务拆解**（后续能力）为多个子 SQL 协同回答 |
| 安全性 | 多数直接执行模型输出 | 生成的 SQL **必须通过独立安全校验层**才可执行 |
| 可验证性 | 无 | 每个输出都能追溯到真实查询结果 |
| 可评测性 | 无 | 独立评测体系（以 Execution Accuracy 为核心） |

## 3. 核心用户

本项目是"电商业务 + 自然语言查数"的产品，主要用户为**非技术角色**，他们不会写 SQL，但每天都需要用数据做决策：

1. **电商运营人员（主力用户）**：问"上个月华东区卖得最好的 5 个品类是什么""最近 7 天退款率有没有上升"，用于选品、活动复盘、日常监控。
2. **管理层 / 业务负责人**：问"今年 GMV 季度趋势""新老客复购率对比"，需要结论 + 图表，而不是 SQL。
3. **数据分析人员（提效用户）**：把高频、固定的取数问题交给 Agent，自己专注复杂建模；同时需要**追溯 SQL** 以校验 Agent 结果（因此 SQL 透明可见是硬需求）。

## 4. 核心业务场景

围绕电商主题（users / products / categories / orders / order_items 及扩展表）：

| 场景 | 示例问题 | 难度 |
|---|---|---|
| 销售额分析 | "2025 年每个月的销售额趋势" | 基础 |
| 商品分析 | "销售额 Top10 的商品，及各自销量" | 普通 |
| 用户分析 | "复购超过 3 次的用户占多少比例" | 普通/多表 |
| 订单分析 | "各订单状态的数量与金额占比" | 基础 |
| 地区分析 | "各省份客单价排名" | 多表 |
| 时间趋势分析 | "同比/环比类问题（需多期对比）" | 复杂 |
| 多维交叉分析 | "按品类 × 地区看 GMV 贡献" | 复杂 |
| 多轮追问 | "看下广东的情况" → "再按月份拆开" → "只算手机品类" | 多轮（后续能力） |

**难度分级**（对齐评测分级，细节见 `evaluation-plan.md`）：

- **基础查询**：单表单条件/简单聚合。例："2025 年订单总数是多少。"
- **普通分析**：单表多条件、分组聚合、排序取 Top。例："各订单状态的数量。"
- **复杂分析**：多表 JOIN、子查询、时间同比环比、多维度交叉、"占比/率"类派生指标。例："月销售额环比增长率。"
- **多轮追问**：依赖对话上下文（指代、条件继承、维度切换、范围修改）——属于后续能力，不在阶段 1 主基线。

## 5. 核心技术问题（必须真正解决的问题）

| # | 问题 | 说明 | 归属 |
|---|---|---|---|
| 1 | Schema 理解与选择（Schema Linking） | 问题中提到"销售额""华南区"，系统如何定位到正确的表与字段；大 schema 直接全量塞给 LLM 会稀释注意力 | **阶段 1 最小基线** |
| 2 | 多表 JOIN 与关系推理 | 主外键路径选择、JOIN 类型判断、聚合前的口径去重（如 order_items 金额 vs orders 金额） | **阶段 1 最小基线** |
| 3 | SQL 生成错误 | 列名幻觉、JOIN 条件错误、聚合层级错误、方言不兼容 | **阶段 1 最小基线**（校验兜底） |
| 4 | SQL 执行错误与自动修复 | 语法错、未知列、类型不匹配、空结果 | 后续扩展（任务书明确要求"SQL 异常自修复"，最终必须实现） |
| 5 | SQL 安全 | 模型生成 SQL ≠ 可安全执行（注入、危险语句、资源耗尽、敏感字段） | **阶段 1 最小基线**（独立安全校验层） |
| 6 | 多轮上下文理解 | 指代消解（"它""那个品类"）、条件继承、维度切换 | 后续扩展（任务书要求，纳入 roadmap） |
| 7 | 复杂分析任务拆解 | 单条 SQL 难以表达的问题（多期对比、跨主题）拆成子任务 | 后续扩展（Secondary/Optional 创新候选） |
| 8 | 结果与结论一致性 | AI 结论必须由查询结果支撑 | 后续扩展（结论生成落地后实现） |
| 9 | 可评测性 | 全套指标的自动化计算、Bad Case 沉淀 | **阶段 1 起即建立**（先以 EX 为核心） |
| 10 | 可追溯性 | 每一步决策可见、可回放，支持评测归因与答辩演示 | **阶段 1 起即建立**（Trace） |

## 6. 功能边界（In Scope / Out of Scope）

### 阶段 1 最小基线（必须做，按此收敛）

> 核心目标：建立**一个最小、可运行、可测试、可量化的 Text2SQL 基线系统**。

- 最小 Text2SQL 基线链（7 阶段，见 `architecture-options.md`）：
  `自然语言问题 → Schema Linking → Few-shot Retrieval → SQL Generation → SQL Validation → SQL Execution → Structured Result`
- SQLite 电商业务库（自建设计 + 合成数据，采用**开发阶段规模**）
- 只读、安全受控的 SQL 执行器（独立安全校验层，强制）
- 基于 EX / Pass@1 / 执行成功率的评测 harness 最小版
- LLM 运行时：**Mimo V2.5 Pro（OpenAI-compatible API）**；开发 Agent：TRAE + DeepSeek-V4-Pro
- 全链路 Trace（可追溯、可复现）

### 后续能力扩展（纳入 roadmap，不在阶段 1 主基线混入）

- SQL Repair（修复循环）
- Task Decomposition（复杂任务拆解）
- Multi-turn Context（多轮追问）
- Result Analysis / Conclusion Generation（结论生成 + 一致性校验）
- Visualization（图表生成，ECharts）
- WebApp 前端（React + Vite + ECharts）
- 用户管理、多 Agent Consensus、Multi-candidate SQL（视评测实验决定，不承诺）

### Out of Scope（明确不做，防止范围蔓延）

- 数据写入类功能（增删改、报表落库）——系统只读
- 多租户/权限体系/登录鉴权（可用单用户模式）
- 对接真实生产数据库与消息队列
- 模型微调/训练（优先 Prompt + 检索工程；作为后续可选研究项，不承诺）
- 复杂报表导出、订阅、定时任务
- 本地部署大模型推理（优先走 API）

## 7. 为什么采用"LangGraph 控制式 Agent"（而不是套路链或自由 ReAct）

1. **需要条件跳转**：校验失败 → 修复 → 重试（后续能力），是**有界循环**；复杂问题 → 拆解（后续能力），是**条件分支**。这些是"状态机"需求，本质契合 LangGraph 的图编排 + checkpoint 能力。
2. **需要多轮状态保持**（后续能力）：follow-up 问题要继承上轮的 schema 选择、SQL、结果上下文。
3. **需要可观测性**：每个节点的输入输出可记录、可回放，支撑评测归因与答辩（LangGraph 的 state 天然可序列化）。
4. **但不用自由 ReAct 作为主架构**：控制流全部在图上**显式定义**（固定主流程 + 条件分支 + 有界循环 + 显式状态），保证可控、可测试、可复现、成本可控，更契合课程项目答辩与评测。
5. **不是为了"Agent"而 Agent**：阶段 1 的最小基线就是一条 7 阶段固定流水线，LangGraph 只负责编排。

---

## 8. 成功标准（项目级）

- 评测集执行准确率等指标有**可量化、可复现的实验数字**（来自本项目真实运行，不采用未验证假设）；
- 每个输出可回溯：问题 → Schema 选择 → 示例 → SQL → 校验 → 结果；
- 评测集分阶段建设：阶段 1 = 100 条单轮 → 阶段 2 = 200 条 + 多轮组 → 最终 = 视质量决定 300～350 条；**Gold SQL 质量优先于数量**；
- 任何优化（Schema Linking、Few-shot、Repair、拆解等）都能用**消融实验**证明有效/无效；
- 所有数字能够回答"这个数字是哪里来的？"（本项目实测 / 文献公开结果 / 明确标注的设计假设）。
