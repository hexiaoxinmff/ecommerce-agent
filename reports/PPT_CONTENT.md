## P2 项目背景与问题

- 标：为什么需要这个系统？
- 传统提数链路：业务问题 → 理解 Schema → 手写 SQL → 检查 → 执行 → 分析
- 三个痛点：
  1. 业务人员不会 SQL —— 运营/管理层提数依赖分析师排期，响应周期长
  2. SQL 需执行验证纠错 —— 生成后要能执行、安全校验、自动修复；单次成功不代表可靠
  3. 本项目定位 —— 不是聊天机器人，而是能执行、验证、纠错、评测的 Text2SQL Agent
- 结论：需要的是 Agent 而非生成器

## P3 项目目标（中心 90.0% EX · 四角能力卡）

- 中心大字：90.0% EX · ECO-SQL-Bench v1.1 执行准确率
- （唯一）目标行：任务书 SQL 执行准确率目标 ≥85%，已达成 —— 只在标题副行出现 1 次，四角卡不重复

## P5 Agent 核心流程（5 阶段 · 全链路 Trace 只出现一次）

- 主标题：用户问题
- 有界约束：repair_count≤1 · execute_count≤2 · 绝不无限循环
- 顶部阶段徽标：阶段1..阶段5（不再逐节点重复“全链路 Trace”）
- 全链路 Trace：页面底部出现一次 —— “全链路 Trace · 状态/失败/Skip/耗时”
- 5 阶段详情：
  1. Schema Linking —— 识别表/字段/置信度（失败 → 受控拒答）
  2. Few-shot 检索 —— 规则型 Top-K 示例（无示例仍可生成）
  3. SQL 生成 —— LLM 生成候选 SQL（进入 Safety 校验）
  4. Safety 校验 —— 独立校验层把关（不安全 → 拦截）
  5. 执行 + Repair —— 失败 → Repair≤1 → Re-check → 重执（仍失败 → 完整诊断）

## P7 SQL 安全与可靠性（三道防线）

- ① Safety：SELECT/WITH 白名单 ｜ 写/多语句拒绝 ｜ AST+Schema 校验 ｜ LIMIT≤500 注入 → 不安全拦截 / 合法放行
- ② 只读：mode=ro ｜ query_only=ON ｜ 500 行截断 → 写操作拒绝 / 结果结构化
- ③ Repair：Repair≤1 次 ｜ 二次校验+执行 ｜ 失败→诊断 → 成功 Result / 仍失败 诊断
- 贯穿：全链路 Trace 留痕
