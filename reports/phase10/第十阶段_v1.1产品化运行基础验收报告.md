## 1. Auth 状态模型（P0-1）

### 1.1 改前的问题

`/api/auth/me` 的**任何**失败都被 `AuthContext` 当成「会话失效」→ 清空会话 → 跳登录页。
于是「后端整个挂了」和「用户确实没登录」在界面上长得一模一样：都是登录页。业务语义是错的。

### 1.2 分派规则（唯一分类源）

分类**只有一个地方**做：`frontend/src/api/http.ts` 的 `classifyRequestFailure(err)`。其余所有判断点（`AuthContext` / `LoginPage` / `AnalysisPage` / `insights.ts`）一律调用它，不再各自写 `err instanceof TypeError`。

| 观测到的事实 | `RequestFailureKind` | `AuthStatus` | 会话 | UI |
|---|---|---|---|---|
| HTTP 200 | — | `authenticated` | 写入 | 进入真实系统 |
| HTTP 401 / 403 | `unauthorized` | `anonymous` | **清空** | 登录页 |
| 网络层失败（`fetch` 抛错） | `backend_unavailable` | `backend_unavailable` | **保留** | 后端不可用页 + 重试 |
| HTTP 5xx | `backend_error` | `backend_error` | **保留** | 后端不可用页 + 重试 |
| 其余 | `other` | `anonymous`（降级） | 清空 | 登录页 |
| 请求未开始 | — | `loading` | — | 「恢复会话中」 |

**关键设计**：只有 401/403 会清会话。网络失败和 5xx **保留会话** —— 服务挂了不是用户登出了。

### 1.3 新增/改动的文件

| 文件 | 作用 |
|---|---|
| `frontend/src/api/http.ts` | 新增 `HttpNetworkError` / `RequestFailureKind` / `classifyRequestFailure()` / `isAbortError()`；`fetch` 包 try/catch（AbortError 原样透传） |
| `frontend/src/auth/AuthContext.tsx` | 重写为五态机；`applySessionFailure()` 为唯一分派点；新增 `retryBackendCheck()` |
| `frontend/src/components/BackendUnavailable.tsx` | 新增。标题「后端服务不可用」+ 说明「请检查后端是否启动」+ `重试` 按钮（`data-testid="backend-unavailable"`） |
| `frontend/src/pages/LoginPage.tsx`、`AnalysisPage.tsx`、`api/insights.ts` | 消除第二个推导源，改用 `classifyRequestFailure` |

### 1.4 禁止回退假数据

`BackendUnavailable.tsx` 里明确写着：

> 本页不会回退到本地假数据：拿不到后端数据，就如实显示为不可用。

浏览器实测中，「后端断开」场景对 10 个历史假数据指纹（`7,662,921` / `1,284` / `352.6` / `+12.4%` / 星耀 / 极光 …）逐页扫描，**0 命中**。

## 3. 启动方式（P0-3 / §五~§八）

### 3.1 审计结论

`backend/` `frontend/` `scripts/` 里**没有**既有的官方启动入口，只有散落在文档里的手动两条命令。因此按任务书 §六，统一收敛为 **`scripts/start_dev.py`**（Python，Windows 优先），并配 `.bat` 包装与 `stop_dev.py`。**没有造第二套启动系统。**

### 3.2 一条命令

```bash
python scripts/start_dev.py            # 前台：Ctrl+C 同时停掉两端
python scripts/start_dev.py --detach   # 后台：进程独立，PID 写 logs/start_dev_pids.json
start_dev.bat                          # Windows 双击；失败自动 pause（窗口不会闪没）
python scripts/stop_dev.py             # 停止（按端口反查真实持有者，杀进程树）
```

成功后输出：

```
==============================================================
Backend : http://127.0.0.1:8000
Frontend: http://localhost:5173
Health  : OK
API 文档: http://127.0.0.1:8000/docs
==============================================================
```

### 3.3 预检 7 步

1. 检查 Python → 2. 检查后端依赖（fastapi/uvicorn/dotenv/pydantic/langgraph/sqlglot/openai）→ 3. 检查 Node → 4. 检查前端依赖（`frontend/node_modules`）→ 5. 检查 `.env` → 6. 检查数据文件（`db/ecommerce.db` + `db/app.db`）→ 7. 检查端口 8000 / 5173 → 启动 Backend → 启动 Frontend → 健康检查 → 输出访问地址。

前端用 `--strictPort`：端口被占就**直接失败**，不会静默换到 5174 让人以为起来了。

### 3.4 其他开关

`--backend-port` / `--frontend-port` / `--env-file` / `--health-timeout` / `--check-only`（只预检不启动）/ `--only {all,backend,frontend}`（单独重启一端）/ `--skip-env-check` / `--skip-data-check` / `--detach`。

### 5.2 两个实测踩到的坑（已修并回归）

- **端口检测漏 IPv6**：Vite 默认绑 `[::1]`，只探测 `127.0.0.1` 会误报「端口空闲」。改为双栈探测，并加回归测试 `test_ipv6_only_listener_is_detected`。

## 6. Health 职责边界（§十）

`/api/health` **只表达三件事**：Backend、Database、Runtime 配置。

- `llm` 字段**只含** `{ provider, model }` —— 是**只读配置回显**，不是能力声明。
- 该接口**不发起任何外部网络调用**（不探活 LLM）。
- UI 侧措辞被约束为「已配置」，**绝不**说「可用 / available / 可达」。

护栏：`backend/tests/test_health_boundary.py`，在 `socket.socket.connect` 层装 egress guard，非 localhost 一律抛错：

- `test_health_makes_no_outbound_network_call` —— 打 health 不触发任何出站连接；
- `test_egress_guard_actually_blocks` —— **反向自查**：护栏自己必须真的能拦住（否则上面那条是假绿）；
- `test_health_llm_field_is_configuration_only` —— `llm` 的 key 集合 ⊆ `{provider, model}`，且整个 JSON 里不出现 `available|reachable|可用`；
- `test_health_status_word_refers_to_service_and_database_only`。

真实 LLM 可用性改由 `POST /api/agent/analyze` 的实际结果表达（见 §8.5）。

### 8.6 过程中修掉的三个「检查器坏了」

这三条都是**测试装置**出问题、却伪装成「被测对象不成立」，代价很高，记录下来：

1. **chrome 启动即崩，表象是 `fetch failed`**：缺 `--no-sandbox` 时，chrome 会先打印 `DevTools listening on ws://...`（看起来已就绪），随后 GPU 进程连崩 6 次并 `FATAL: GPU process isn't usable. Goodbye.` 自杀（exit `0x80000003`）。表象与「代理问题」完全同形。**修**：加 `--no-sandbox`，且 chrome 的 stdout/stderr 必须收进环形缓冲随错误一起抛出（原来 `stdio:"ignore"` 把 FATAL 行吞了）。
2. **服务栈「看起来还在跑」其实已经没了**：在受限执行环境里，被某次命令启动的 `--detach` 子进程会随该次命令结束而消失（后端日志停在 `GET /api/health 200`，无任何 shutdown 行）。脚本若假设服务还在，就会把「服务早没了」误报成「后端断开场景不成立」。**修**：服务栈由实测脚本**自己**拉起，生命周期自洽；「启动」本身也进入断言。
3. **负对照差点变成假绿**：见 §8.2。

## 11. 报告数字的可复算性

本报告里每一个数字（1031 passed / 18 endpoints / `5824f7dd` / `3ac09864…` / 55/55 / `id=67` …）
都是人手敲进去的。**人手敲进去的数字不等于事实** —— 它可能来自上一轮的记忆、来自中途失败的一次跑、
来自复制粘贴时的手滑。

所以配了一个只读对账器：

```bash
python scripts/audit_phase10_report_numbers.py
```

它做三件事：

1. **重算真值**：从原始产物出发 —— 直接 import FastAPI app 推导端点、解析 pytest JUnit XML、
   解析 vitest JSON、重算 ZIP SHA256、扫描 `_delivery_build` mtime（铁律 2：porcelain 看不见
   未跟踪文件内部改动，只能用 mtime）、读取浏览器实测 JSON、解析 `start_dev.py` 的 `EXIT_` 常量、
   重跑 `git status` 与归档基线做差集；
2. **抽取声称值**：用正则从**本报告文本**里抓出每个数字，与真值逐项断言相等；
3. **反向自查**：把报告文本改坏两个数字（`1031 → 9999`、`5824f7dd → deadbeef`），
   对账器必须比原来**多报**失败 —— 否则它就是个恒绿的摆设。

当前状态：

```
===== ALL_PASS  40/40 =====
反向自查：改坏数字后必须多报失败 — 原版失败=0 变异后失败=2
```

对账器本身也踩到一个坑并已记录：`importlib.util.module_from_spec()` 创建的模块
**必须先注册进 `sys.modules`**，否则模块里的 `@dataclass` 会因
`sys.modules[cls.__module__]` 为 `None` 而炸（`AttributeError: 'NoneType' object has no attribute '__dict__'`）。

> 本对账器只**读**，不改任何产物。它第一次跑就抓出 4 处不一致（3 处是我的正则写错、
> 1 处是报告漏算了它自己这个新文件），全部修正后才到全绿。

### 11.1 一个必须说清楚的自指陷阱

对账器接进 pytest 之后**立刻变红了一次**，原因是它自己造成的：

> pytest 的 JUnit XML 是**本次运行结束时**才写盘的。
> 所以在套件内部读 `pytest_narrow.xml`，读到的必然是**上一轮**的产物 ——
> 于是「本轮新增了 3 条测试」会被误报成「报告里写的 1028 是错的」。

这类检查叫**自指项**（依赖被测系统自己产出的证据）。处理方式**不是放宽判据**，
而是给它们打标记并在套件内跳过：

```bash
python scripts/audit_phase10_report_numbers.py                          # 全量（产物落盘后跑）
python scripts/audit_phase10_report_numbers.py --skip-self-referential   # 套件内跑
```

| 模式 | 对账项 | 反向自查 |
|---|---:|---|
| 全量 | **54/54** | 原版 0 → 变异后 **2** |
| 套件内（跳过自指） | **43/43** | 原版 0 → 变异后 **1** |

套件内变异只 +1，是因为 pytest 计数那一项被跳过了 —— 少一个变异生效，
反向自查就少报一条，这是**预期行为**，不是护栏变松。

变异目标也是**从报告文本里现找**的（正则匹配后替换），不硬编码 `1028` 这种具体数字；
否则每次报告数字正常变动，变异都会失效，护栏会自己变脆。
