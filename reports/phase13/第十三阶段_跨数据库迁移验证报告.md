## 2. Agent Core / Adapter 边界

```
Agent Core（本阶段 0 行改动）
  agent/graph.py    固定流程：link → fewshot → generate → safety → execute →(repair)→ result
  agent/nodes.py    AgentComponents 依赖注入容器
  sqlgen/safety.py、sqlcheck/scope_validator.py、sqlexec/executor.py   安全/范围/执行（逻辑领域无关）
  evaluation/runner.py、evaluation/metrics.py                          评测核心（可注入 runner/executor）

Adapter Layer（本阶段新建/参数化）
  dbprofile/models.py    Profile 数据结构（schema / business_rules / fewshot 三层）
  dbprofile/profiles.py  内置注册表：ecommerce_A、ecommerce_B + resolve_profile()
  dbprofile/adapter.py   DatabaseAdapter：连接、Schema 目录（per-profile 缓存）、
                         Few-shot 装配、执行器绑定、components_for_profile()
```

边界结论：**「Agent 编排 + 安全校验 + 评测」是通用能力；「Schema 白名单与描述、业务口径文本、Few-shot、检索词表、连接」是业务适配能力。** 换库时前者不动，后者整体替换。

## 4. Business Rules Profile

明确区分两个层次：**数据库结构**（表/字段名，内省可得）与**业务口径**（销售额用什么字段、取消叫什么、枚举是什么，内省不可得）。后者是 Prompt 里真正不可迁移的部分，因此按消费方拆成四份文本注入：

| 文本 | 注入点 | A（冻结基线原文） | B（本阶段新写） |
|---|---|---|---|
| generation_rules | `sqlgen/prompt.py build_prompt(business_rules=...)` | subtotal=销售额；total_amount=明细−优惠+运费；排除 `cancelled`；15 省枚举 | line_total=销售额；payment_due=明细−抵扣+配送费；排除 `voided`；城市须 JOIN members；15 城枚举；is_active 整数；tier 枚举 |

| repair_rules | `sqlrepair/prompt.py build_repair_prompt(business_rules=...)` | 同上 | 同上 |
| schema_link_example | 链接示例 JSON | orders/order_items/products 示例 | sales_orders/order_lines/items 示例 |

全部为**可选注入参数，缺省 None = 原常量**，冻结基线 Prompt 逐字节不变（测试固化）。

## 6. 第二数据库设计（db/ecommerce_v2.db，B 公司：连锁零售会员制门店）

**不是复制改名**。与 A 库的结构性差异：

| 差异点 | A（ecommerce.db） | B（ecommerce_v2.db） |
|---|---|---|
| 表名 | users / categories / products / orders / order_items | members / departments / items / sales_orders / order_lines |
| 字段名 | username, region, register_date, status, price, order_date, discount_amount, shipping_fee, total_amount, quantity, unit_price, subtotal | member_name, city, joined_on, tier, is_active, list_price, placed_on, coupon_deduction, delivery_charge, payment_due, qty, deal_price, line_total |
| 表关系 ① | categories 两级层级（parent_id，商品挂叶子） | departments **单层无层级** |
| 表关系 ② | orders 自带 region 冗余列（地区分析免 JOIN） | sales_orders **无城市列**，城市维度必须 JOIN members（关系型语义差异） |
| 业务语义 ① | 取消 = `status='cancelled'`；金额字段「销售额=subtotal / 实付=total_amount」 | 作废 = `order_state='voided'`（cancelled 取值不存在）；「销售额=line_total / 实付=payment_due」 |
| 业务语义 ② | status 文本枚举（active/inactive、on_sale/off_sale） | is_active **整数** 1/0；availability（in_stock/discontinued）；tier（gold/silver/bronze，A 无此维度） |
| 业务语义 ③ | unit_price 恒等于标价 price | deal_price 为成交快照，约 15% 明细低于 list_price（9 折成交） |
| 数据规模/时间 | 2,000 用户 / 10,000 订单 / 500 商品 / 2024-01~2026-09 | 1,200 会员 / 6,000 订单 / 150 商品 / 2025-10~2026-09（新公司仅近一年） |

物化口径约束（建库脚本内建验证，并有测试固化）：非作废订单 `payment_due = ROUND(Σline_total − coupon_deduction + delivery_charge, 2)`；作废订单三项金额全为 0。

生成与复现：`scripts/generate_data_v2.py`（seed=20260928，确定性）+ `scripts/init_db_v2.py`；两次初始化行数完全一致（departments 6 / items 150 / members 1,200 / sales_orders 6,000 / order_lines 15,264）。`db/ecommerce.db` 原库 mtime 保持 2026-09-14 未被触碰。

失败样本证据（第二批 pred SQL 摘录）：

- **Exp B 的 borrowed 口径移植（8 题，全部「执行成功但数值错」）**：`WHERE order_state != 'cancelled'`（B 库无 cancelled 取值，过滤**静默失效**，作废订单被计入销售额/客单价等，X-006/007/009/010/011/019/024）；`availability = 'on_sale'`（A 的枚举值，X-002）。
- **Exp B 的结构移植（4 题）**：照抄 A 的 `order_items.order_id` 命名生成 `JOIN order_lines ol ON ol.order_id = so.id` → `no such column: ol.order_id` 执行失败（X-008/014/017/022），且 Repair 因同样携带 A 知识而修复失败——**错误的知识连修复环节一起污染**。
- **Exp A 与 Exp C 的共同残余失败（X-006/010/017，两批均现）**：两库上模型都把「销售额」默认成订单级实付字段（A：`SUM(total_amount)`；C：`SUM(payment_due)`），而不是 Profile 规定的明细口径（`subtotal` / `line_total`）。这是**基线模型自身的口径遵循弱点**，与换库无关——两库失败形态逐字段对应，恰好证明 C 组已恢复到与 A 同构的能力状态。
- **其余残余失败均为一次性输出抖动**：A 组 X-018（平均售价多加了在售过滤）与 X-014/X-009（第一批/第二批分别在月度趋势、地区销售额上抖动）；C 组 X-009（生成阶段 Schema 校验拦截）、X-022（只输出类目名漏掉指标列）。注：Repair 机制按设计只接管「执行阶段」错误，不接管生成阶段校验失败（与 A 库行为一致，非适配层缺口）。

## 10. 最终结论（基于真实实验数据，两批运行一致）

### 10.1 问题 1：换数据库是否影响效果？
**是，影响显著且可精确归因。** 同一 24 题、同一模型：A 库 75.00% → B 库零适配（B0）结构不可用；最低限度适配（B 组）50.00%（−25pp；第一批 −29.17pp），其中 8 题是口径移植导致的「静默错误」（SQL 合法执行但数值错误，如 `cancelled` 过滤失效），4 题是结构错误。

### 10.2 问题 2：哪些问题来自 Schema？
表名/字段名/关系差异造成的是**显性失败**：执行报错（`no such column: ol.order_id`）或可被校验拦截。在 B 组中占 4 题（两批一致复现）。这类问题由 Adapter 的结构层（内省 + 白名单 + 描述）一次性解决：C 组结构错误清零（仅剩 1 题生成阶段校验拦截，属模型输出抖动）。

### 10.3 问题 3：哪些问题来自业务语义？
这是**最大损失来源（B 组 8/12 失败）**，且更危险：口径移植错误（`cancelled` 过滤在 B 库静默失效、`on_sale` 枚举不存在）全部能**合法执行**，返回看似合理但错误的数值，不报错、只错数。解决它靠的不是代码而是**知识**——Business Rules Profile 文本 + Few-shot。C 组该项清零。

### 10.4 问题 4：Few-shot / Business Rules Adapter 是否有效？
**有效。** C 组（B 库 + B Profile）EX 75.00%，较 B 组 +25pp，恢复 B 组全部损失（第一批恢复 25/29.17 = 86%）；与 A 基线差距 0pp（第二批 75.00% = 75.00%）。C 组残余失败集 {006,009,010,014,017,022} 与 A 组残余失败集 {006,009,010,014,017,018} 有 5/6 重合，且重合题在两库上的错误形态逐字段对应（`total_amount` ↔ `payment_due`）。即：**适配层把系统恢复到「换了一个库的基线」状态，而不是魔法地超越基线**——这正是可迁移性的正确含义。

### 10.5 问题 5：Database Profile 是否能降低迁移成本？
**能，且成本结构被改变。** 改造成本一次性（12 个文件的参数化 + dbprofile 包 608 行），之后每个新库的边际成本 = 纯数据/文本（1 个 Profile ≈ 125 行 + 建库脚本），代码改动为 0；`DB_PROFILE` 环境变量（或 `resolve_profile()`）即可完成 A↔B 切换。同进程 A→B→A 反复切换已由测试固化（目录缓存按 Profile 隔离，21 项测试全过，含 fake Provider 端到端跑通两库）。冻结线复核：v1.0 ZIP SHA256（`3ac09864…A30F`）与 `_delivery_build/` 1822 文件快照哈希在阶段开始与结束时完全一致。

### 10.7 诚实的边界（不夸大）
1. 仅验证 **SQLite**；方言差异（PostgreSQL/MySQL）未覆盖，`db_type` 字段是未来的扩展点而非已实现能力。
2. B 库为同构电商场景（会员制零售）；跨**行业**差异（金融/制造）未验证——那是 FewShotProfile 的后续行业包问题。
3. 仍有残留绑定未 Profile 化（不在 Agent 主链路）：`insights.py` 看板固定 SQL、`/api/system/schema` 的 A 表字段响应模型、`fanout_detector` 的 orders×order_items 常量、E8/E11 条件契约的主键映射（默认关闭）。接入 B 库对外服务前需处理前两项。
4. 24 题实验规模小于正式 Benchmark（100 题）；结论在题目类别维度结构完整，但单类别样本量小（1~5 题），1 题 = 4.17pp，批间方差即此量级（两批运行已给出实证）。
5. 本机 `.env` 实际生效模型为 `deepseek-chat`（mimo Provider 兼容层），三组一致；与冻结基准模型不可比，本报告所有对比均在同环境内成立。
6. 既有测试套件中 4 个失败为**改动前已存在**（3 个 LLM 工厂测试与本机 `.env` 交互、1 个 Phase10 报告与 git 工件对账），与 Phase 13 无关；Phase 13 新增 21 项测试全过，全套其余 1054 项通过。
