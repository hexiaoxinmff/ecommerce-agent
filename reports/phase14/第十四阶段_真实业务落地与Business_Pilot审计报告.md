## 2. 当前产品真实定位

**从代码与 UI 反推的真实定位**（不是 PRD 里的定位，是当前实现实际支持的定位）：

> 一个**单轮、只读、单库**的电商数据速查工具：运营人员用自然语言问一个「能被 5 张表回答」的问题，系统在约 2 秒内返回真实数字与可追溯证据（SQL/Trace/历史），辅助日常运营判断。

当前实现**支持**的：单轮问答、全链路 Trace、查询历史、只读安全、Dashboard 固定 KPI、Schema 查看页。
当前实现**不支持**的（代码证据）：多轮追问（`AgentRequest` 仅单条 `question` 字段）、导出（全仓 grep `csv/导出` 零命中）、指标口径说明（无 tooltip/解释字段，`AgentResponse` 无自然语言解释字段）、时间范围声明（分析页结果卡无 as_of）、诚实的拒绝（无「无法回答」通道，见 §6.3）。

**不是**：BI 平台、多租户数据产品、对话式分析师、自动归因系统。

## 3. 第一目标用户

**结论：电商运营人员（运营专员/运营助理），不含数据与技术人员。**

从三个真实证据反推：

1. **Dashboard 的信息结构就是运营日报**：`insights.py` 固定返回「本月销售额 / 订单量 / 注册用户 / 客单价 + 12 月销售趋势 + 叶子类目 Top5 + 商品销售 Top5」——这是运营晨会视角，不是财务（无毛利/成本）、不是产品（无漏斗/留存）、不是数据（无明细导出）视角。
2. **前端示例问题全部是运营口吻**：`uiCopy.ts` 的 11 个示例（本月销售额、近三月趋势、销售额 Top5 商品、类目销售额、各地区订单量）没有一个需要 SQL 知识或跨表深度分析。
3. **数据结构决定了可回答域**：5 张表（users/categories/products/orders/order_items）覆盖「卖得怎么样、谁在买、什么好卖、哪里好卖」——运营日常问题；库中没有埋点/成本/供应链/客服数据，分析师与产品经理的核心问题在此库上不可答。

**排除理由**：数据人员会要求导出与自写 SQL（当前无导出，SQL 面板只读展示）；业务分析人员需要多维透视与口径自定义（不支持）；管理人员要的是结论与趋势解读（当前无解释生成，README §17 明示「结论生成未实现」）。这些角色**不是不需要**，而是当前版本给不了他们完整价值；运营人员的高频、短平快、单轮问题恰好落在当前能力圈内。

## 4. 第一业务场景与真实业务闭环

### 4.1 用户原来怎么完成这件事

运营专员想回答「这个类目最近卖得怎么样」：

1. 自己不会 SQL → 提数据需求/找数据同学排期 → 等 T+1 或数小时；
2. 或打开现成报表 → 报表没有这个切角（地区×类目×时间窗组合爆炸，固定报表覆盖不了）；
3. 或让老板等。

**当前 Agent 替用户完成的一步**：把「提需求 → 排期 → 写 SQL → 核对 → 出数」压缩为「打一句话 → 约 2 秒 → 得到数字与证据」。节省的主要是**沟通与等待成本**，不是替代 BI 的深度分析。

### 4.2 业务闭环与最薄弱环节

```text
业务问题 → 用户提问 → Agent 理解 → 业务规则/Schema → SQL → 安全校验
        → 真实数据库 → 结果 → 解释 → 业务决策
```

| 环节 | 实测状态 | 评价 |
|---|---|---|
| 用户提问 | 示例可点击但不自动执行；无口径提示 | 中 |
| Agent 理解 | Schema Linking 正常；时间词理解有系统性错误（§7.2） | **薄弱** |
| 业务规则/Schema | 规则文本存在但关键口径遵循弱（§7.1） | **薄弱** |
| SQL 生成 | 22/22 生成成功 | 强 |
| 安全校验 | 0 拒绝、0 误伤 | 强 |
| 真实数据库 | 22/22 执行成功，P95 ≈ 2.0s | 强 |
| 结果 | 表格/KPI/图，但英文列名、无口径、无时间标注 | **薄弱** |
| 解释 | 无自然语言解释；用户追溯终点是裸 SQL | **最薄弱** |
| 业务决策 | 无「下一步」引导；无导出；无追问 | 薄弱 |

**闭环最薄弱的一步：解释环节。** 链路中段（SQL→安全→执行）工程化最好（执行成功率 100%），但「结果→解释→业务决策」这一段几乎完全空白：用户拿到一个带英文列名的数字，不知道口径（明细还是实付？含不含取消单？）、不知道时间范围（"本月"是哪个本月？）、不知道概念是否真的存在（§6.3 陷阱题）。**对一个不懂 SQL 的目标用户，等于结果不可验证。** 次薄弱是时间语义（§7.2，会让"结果"本身直接错误）。

## 6. 当前 Agent 真实能力（P20 × 22 题真实运行）

运行方式：复用正式评测核心 `evaluation/runner.py::eval_single_item`（Agent Core 零改动），真实调用 `run_agent()`（当前运行配置）。逐题产物：`reports/phase14/rbq_audit_results.json`。

### 6.1 总量指标

| 指标 | 实测值（2026-10-02） |
|---|---|
| SQL 生成成功 | 22/22（100%） |
| **执行成功率** | **22/22（100%）** |
| **EX（结果与业务口径 gold 等价）** | **13/22（59.1%）** |
| SQL Error（生成/安全/Schema 校验拒绝） | **0** |
| Execution Error（执行报错，含 Repair 后仍失败） | **0** |
| Repair 触发 | 0 次（全部一次通过） |
| Provider 失败 | 0 |
| 延迟 | avg 1.73s / p50 1.73s / p95 1.99s（deepseek-chat） |

**核心事实：所有失败都是「执行成功但结果错误」。** 没有一题报错——SQL Error 与 Execution Error 均为 0。危险完全集中在静默错误区。

### 6.2 失败分类（9 题）

| 类别 | 题数 | 明细 | 性质 |
|---|---|---|---|
| **Silent Wrong（口径错误）** | 4 | RBQ-004/007/012/014：用 `SUM(total_amount)` 回答「销售额」，而非 Profile 规定的明细口径 `SUM(order_items.subtotal)` | 执行成功、数值系统性偏低约 4.5%（33,206,362 vs 31,705,588），用户无从察觉 |
| **Silent Wrong（时间漂移）** | 3 | RBQ-011/013/021：用 `date('now')/strftime('now')` 锚定真实时钟 2026-10，而库数据止于 2026-09-12 | 「本月销售额」直接返回 **None**；「上月」返回部分月，数值仅为正确答案的 33%；「近30天」窗口实际只剩 11 天，Top5 排名错 3 个 |
| **形态差异（soft fail）** | 2 | RBQ-006（返回全量 30 行排名，gold 要求 Top1——第一行即正确答案）；RBQ-020（LEFT JOIN 保留 0 商品的父类目） | 答案包含在结果中，业务上可接受；属评测严格性而非业务错误 |

按业务视角修正：**首次回答业务可用率 ≈ 15/22（68.2%）**（含 2 题形态 soft pass）；严格口径 EX 59.1%。

### 6.3 陷阱题：0/4 诚实拒绝，4/4 静默编造

| 陷阱题 | Agent 实际行为 | 评审 |
|---|---|---|
| TRAP-001「最近卖得怎么样？」 | 静默自选 `date('now','-30 day')` 窗口（因漂移实际只有 11 天数据），返回 73.4 万，**未声明窗口** | 静默编造窗口 |
| TRAP-002「有多少 VIP 用户？」 | **静默把 VIP 等同于 `users.status='active'`**，返回 1707 | 概念杜撰（库中无 VIP 概念） |
| TRAP-003「退款金额一共有多少？」 | 返回 `SUM(total_amount) WHERE cancelled` = **0.0** 冒充退款额 | 口径杜撰（478 笔取消单金额清零 ≠ 没有退款损失） |
| TRAP-004「上月销售额环比？」 | 两期都用漂移窗口（部分月 9 月 vs 完整 8 月），返回 -144 万 | 双重错误静默输出 |

**结论：Agent 没有任何「无法回答/概念不存在」的表达通道。** 面对库中不存在的概念，100% 编造一个看似确定的数字。这与响应结构有关：`AgentResponse` 无自然语言解释字段，模型唯一的出口就是 SQL。

### 6.4 与历史基线的关系

- 冻结基线 90.0% EX（ECO-SQL-Bench v1.1 / mimo-v2.5-pro）**不可直接对比**：题集不同、模型不同（当前运行时 deepseek-chat 从未跑过冻结 Benchmark）。
- 但失败模式与 Phase 13 高度一致：Phase 13 Exp A 残余失败 X-006/010/017 正是「销售额默认用订单级实付字段」；本审计在新鲜题、运营口吻下复现为 4 题。**这是当前运行模型的系统性口径遵循弱点，不是偶发。**
- Phase 13 已证明的能力保持有效：执行链路稳定（Exec 100%）、无结构性 Schema 错误。

## 7. 业务语义风险（按危险度排序）

### 7.1 风险一：销售额口径的「双真相源」

- Agent 侧规则（`sqlgen/prompt.py` BUSINESS_RULES）：「销售额」= `order_items.subtotal`（明细口径）；
- Dashboard 侧实现（`insights.py` `_SQL_MONTH_KPI`）：「本月销售额」= `SUM(orders.total_amount)`（订单实付口径）；
- 实测差值：全库两种口径相差 **150 万元（33,206,362 vs 31,705,588，4.5%）**；月度差值同量级。

运营人员在 Dashboard 看到「本月销售额 X」，转身问 Agent 同一个问题得到 Y（且 Agent 还有 4/22 概率直接用错字段），**没有任何页面解释两者为什么不同**。KPI Definition 没有独立层，两个消费方各自硬编码——这是「业务语义层缺失」的最直接体现。

### 7.2 风险二：相对时间锚定错误（随时间恶化的定时炸弹）

静态库数据止于 **2026-09-12**，真实时钟 **2026-10-02**（漂移 20 天且持续扩大）：

| 问题 | Agent 实际窗口 | 实测结果 | 业务真相 |
|---|---|---|---|
| 本月销售额 | `strftime('%Y-%m','now')` = 2026-10 | **None（空）** | 最新数据月 2026-09 = 82.6 万 |
| 近 7 天订单量 | `date('now','-7 day')` = 2026-09-25 起 | **0** | 09-06~09-12 = 322 笔 |
| 近 30 天销量 Top5 | 2026-09-02 起（仅 11 天） | Top5 错 3 个 | 30 天窗口 08-14~09-12 |
| 上月销售额 | `now-1 month` = 2026-09（12 天部分月） | 76.6 万（33%） | 完整 8 月 = 231.4 万 |

Few-shot 示例（`ex_001/ex_004/ex_005`）本身就用 `date('now')` 写法，**把漂移机制教给了模型**。Dashboard 曾用 D1 决策（本月=MAX(order_date) 所在月）绕开此问题，但该契约**只存在于 Dashboard 代码注释里，从未进入 Agent 的 Prompt/规则/Few-shot**。数据时效契约（as_of）缺失是全链路性的。

### 7.3 风险三：不可回答问题的编造（§6.3）

库中无 VIP/退款/成本/转化漏斗概念。Agent 无拒绝通道，陷阱题 0/4 诚实拒绝。运营人员问「退款多少」得到「0.0 元」会得出「没有退款损失」的错误业务结论。

### 7.4 风险四：Repair 污染（复核 Phase 13 结论）

本审计 22 题零 Repair 触发（错误全部是静默语义错误，Repair 按设计只接管执行错误）。Phase 13 已证明：错误知识会同时污染生成与修复环节（Exp B 4 题结构错误 Repair 全败）。当前风险 dormant 但机制性存在。

## 8. 当前产品使用体验（用户视角走查）

对 8 个体验问题的结论（完整证据见附录产物；全部有 file:line 证据）：

| # | 问题 | 评级 | 关键发现 |
|---|---|---|---|
| 1 | 知道该问什么吗 | 中 | 示例 11 个可点击但**点击只回填不执行**；无时间/口径提示 |
| 2 | 能理解结果吗 | 中 | 形态齐备（KPI/表/图），但**列名是英文 SQL 别名**（`total_sales`）；空结果无提示，图表占位文案误导 |
| 3 | 知道时间范围吗 | 首页优/分析页**差** | 首页有 as_of（做得好）；**分析页结果无任何时间标注** |
| 4 | 知道指标口径吗 | **差** | 全站无口径说明；「销售额=subtotal、排除 cancelled」只存在于代码注释；DatasetsPage 有字段说明但与结果页零联动 |
| 5 | 能追溯吗 | **优** | SQL/Trace/执行过程默认折叠可展开、失败保留证据——诚实性工程是全项目亮点 |
| 6 | 失败知道发生了什么 | 中 | 错误四分类清晰；但 LLM 错误英文原文透传（"Mimo authentication failed"） |
| 7 | 下一步做什么 | **差** | 无追问/导出/保存；History 无「重新发起」；RecentActivity 回填到**首页演示框** |
| 8 | 必须懂 SQL 吗 | 中 | 使用不需要；但**不依赖 SQL 的口径验证手段为零** |

**P0 级 UX 断点——首页假分析**：`HomePage.tsx` 首页提问框是纯 700ms/阶段的定时器动画（不调用任何 API），任意问题「分析完成」后固定显示 `overview.kpis.month_sales`（本月销售额）并打「数据来源：真实只读聚合」徽标。虽有底部小字声明「界面演示，未真实执行」，但第一视觉是大数字+真实徽标。**第一次使用的运营人员问「哪个商品销量最高」，得到「本月销售额 76 万」并可能信以为真**——这是当前全产品最危险的单点。

其余量化缺陷：结果表截断文案「前 500 行」与实际 50 行不符（`ResultTable.tsx`）；"执行诊断"柱状图对业务用户无价值占半屏；系统设置为纯占位页。

## 9. Business Pilot 最小闭环（MVP Pilot 设计）

> 以下为方案设计，**本阶段不执行**。原则：真实库/真人/真问题/真 Agent/真历史/真反馈，六真缺一不可；反馈机制先用零代码表格，验证有人用之后再改产品。

```text
Pilot User
  1 名电商运营专员（主用户，非技术）+ 1 名运营主管（验收方）+ 项目组 1 人（陪跑/答疑）
  前提：能接受「演示合成数据」这一事实（当前库为合成电商数据）

Pilot Scenario
  「运营日常销售速查」：每日开屏看 Dashboard KPI → 用自然语言追问细节
  （某类目/地区/时间窗的销售、Top 榜、状态分布）→ 参考结果做当日运营动作

Pilot Question Set
  起步 = RBQ-P20（22 题，已实测基线：Exec 100% / EX 59.1%）
  试点期自然累积用户真实问题（预期每周 10~30 条，进入 EXT 池）

Pilot Success Criteria（观察期末同时满足）
  S1 执行成功率 ≥ 95%（技术底线，已达标）
  S2 首次回答可用率 ≥ 70%（用户逐条标 👍/👎 后换算）
  S3 抽检静默错误率 ≤ 10%（项目组每周抽 10 条人工核对口径/时间窗）
  S4 观察期末用户自愿继续使用（第 2 周使用天数 ≥ 第 1 周）
  S5 高频失败题收敛：同一问题连续失败 ≤ 2 次即有修复动作

Pilot Failure Criteria（触发即暂停试点）
  F1 用户基于结果做出错误业务决策且源头是静默错误（口径/时间）
  F2 S3 连续两周 > 10%
  F3 平均等待 > 10s 或失败率 > 20% 导致放弃
  F4 用户第 2 周起不再自发使用

Pilot Feedback Method（零代码起步）
  每条结果旁人工记录三列：可用？/ 口径对吗？/ 想要但没有的？
  （若最小改造先行：结果卡加 👍/👎 + 原因标签，升级为结构化数据）

Pilot Observation Period
  2 周（10 个工作日），每工作日 15~30 分钟真实使用；
  第 5 个工作日中期检查点，第 10 个工作日出 Pilot 结论
```

**Pilot 前置条件（P0 必须先修，见 §11）**：时间锚定修复、销售额口径修复、首页假分析移除。**不修这三项直接试点，F1（静默错误导致错误决策）几乎必然触发。**

## 10. Business KPI（第一版）

> 标注规则：✅ = 本审计已实测；📏 = 已定义度量方法、**尚未实测**（Pilot 采集）。

### 技术指标

| 指标 | 定义 | 基线（本次审计） | Pilot 目标区间 |
|---|---|---|---|
| Execution Success Rate | 执行成功/总问题 | **100%** ✅（22/22） | ≥95% |
| Silent Wrong Rate | 执行成功但业务口径/时间窗错误 / 总问题 | **31.8%** ✅（7/22，口径 4 + 时间 3） | **≤10%（最关键指标）** |
| Query Success Rate（EX） | 结果与业务口径等价/总问题 | **59.1%** ✅ | ≥70%（首轮） |
| Average Latency | 端到端 | **1.73s** ✅ | ≤5s |
| P95 Latency | 端到端 | **1.99s** ✅ | ≤10s |

### 业务指标

| 指标 | 定义 | 现状 | Pilot 目标区间 |
|---|---|---|---|
| 用户问题解决率 | 用户自评「解决了我的问题」/总问题 | 📏 未实测 | ≥70% |
| 首次回答可用率 | 无需重问/换问法即得到可用答案 | 📏 未实测（EX 59.1% 为技术上界参考） | ≥70% |
| 人工修改率 | 用户需要自己换算/核对/改口径的比例 | 📏 未实测 | ≤30% |
| 重复提问率 | 同一问题 7 天内被再次提问（隐含上次不满意） | 📏 未实测（History 可计算） | ≤20% |
| 业务人员满意度 | 试点期末 5 分制 | 📏 未实测 | ≥3.5/5 |
| 高频失败问题数 | 周期内失败 ≥2 次的独立问题数 | 本次 9 题（P20 内）📏 | 试点末 ≤3 且有修复计划 |

### 「什么结果才值得继续投入」判定线

> **继续投入**：Pilot 两周内 Silent Wrong Rate ≤10% 且问题解决率 ≥70%，且用户第 2 周自发使用不衰减——说明该工具已进入「省等待成本」的真实价值区。
> **收敛修复**：解决率 40~70% 区间且失败集中于可枚举的口径/时间问题 → 先修语义层再扩试点。
> **停止投入**：Silent Wrong Rate 持续 >20%，或用户明确表示「不如直接找数据同学」且第 2 周使用归零——说明单轮速查形态不成立，需重新定位而不是继续加功能。

## 11. P0/P1/P2 问题（严格排序）

### P0：不解决就无法进行真实业务试用（3 项，均为最小改造）

| # | 问题 | 证据 | 最小改造方案 | 预估规模 |
|---|---|---|---|---|
| P0-1 | 相对时间锚定错误：`date('now')` 对静态库系统性静默出错（本月=None、上月=33%、近7天=0） | §7.2 实测 3/22 题 + 陷阱题 1 | 把「数据时效契约」注入 A Profile 业务规则文本：声明数据截止日为 2026-09-12、相对时间以 `MAX(order_date)` 为锚（与 Dashboard D1 决策对齐）；同步修正 3 条 fewshot 示例的 now 写法；响应侧复用现有 `as_of` 机制在结果卡展示 | Profile 文本 + 数据文件，Agent Core 0 行；需 RBQ-P20 + Benchmark 冒烟回归 |
| P0-2 | 销售额口径静默错误 + Dashboard/Agent 双口径 | §7.1 实测 4/22 题；两种口径差 150 万 | ① 将已有但默认关闭的 `METRIC_SEMANTICS_RULES`（E5，「商品/类目销售额→subtotal」决策表）并入 A Profile 的 generation_rules（或开启 SQLGEN_EXTRA_RULES=E5），用 P20 回归验证；② Dashboard「本月销售额」补口径标签（明细口径 or 实付口径二选一对齐 Agent），短期先在 KPI 卡注明口径 | ①纯文本/配置；②前端 1 个标签；均不碰冻结资产 |
| P0-3 | 首页假分析：任意问题返回固定「本月销售额」并标「真实」徽标 | `HomePage.tsx:151-173,279` | 移除假结果区或改为「去智能分析页真实提问」跳转（后者推荐，保留演示动画但去掉假结果大数字） | 前端单页改造 |

### P1：会明显影响真实用户体验（试点前做或试点中快速跟进）

1. **结果无时间标注**：分析页结果卡展示数据 as_of 与问题涉及的时间窗（后端响应已有数据源，前端补展示）。
2. **英文列名**：结果表/KPI 标签无中英映射——最小方案：Profile 增加列名→中文映射字典（数据文件），前端查表回退英文。
3. **不可回答问题无拒绝通道**：最低成本 = Profile 规则加「概念不存在时使用空结果 + SQL 注释说明」不可行；推荐在生成 Prompt 加一条「无法从给定 Schema 回答时，输出带 `CANNOT_ANSWER` 标记的 JSON」+ 前端识别文案（属最小结构性改动，试点前完成 P0 后评估）。
4. **空结果文案**：0 行时明确「查询结果为空（可能因时间窗内无数据）」；修正「前 500 行」截断文案。
5. **LLM 错误文案中文化**：`llm.py` 错误映射表加中文对照。
6. **History 无重新发起**：历史条目加「再次分析」跳转（复用现有路由）。
7. **示例点击即执行**：分析页示例 chip 点击后直接 runAnalysis。

### P2：可以在试点后优化

导出 CSV、多轮追问、诊断图表替换为业务图表、DatasetsPage 字段说明与结果页联动、Profile 切换接入运行时 API（当前 `/api/agent/analyze` 固定 `default_components()`，`components_for_profile()` 仅实验可达——单公司试点期可接受）、汇报模式打磨、登录限流。

### 暂缓：目前完全不值得做（除非试点证据要求）

多 Agent 编排、向量数据库（规则检索 22/22 fewshot 命中无瓶颈）、微服务化、企业级权限中心（现有 Bearer + 只读够用）、自动 BI/归因、多租户、监控平台、复杂前端、PostgreSQL/MySQL 方言适配（Phase 13 已声明边界）、多轮对话上下文（单轮速查场景下优先级低于口径正确性）。

各层解耦状态：

| 层 | 状态 | 证据 |
|---|---|---|
| Agent Core | ✅ 已解耦 | `backend/app/agent/` 零电商字符串（Phase 13 验证，本次复核未变） |
| Database Adapter | ✅ 已解耦 | `get_connection_for()` / `allowed_tables` 参数化；Profile A 默认值兼容 |
| Business Profile（口径文本/Few-shot/Schema 描述） | ✅ 已独立成层 | `dbprofile/` 三层结构；A/B Profile 切换有 21 项测试固化 |

| Schema 信息 | ✅ 已独立 | 内省 + Profile 描述层 |
| 数据库连接 | ✅ 已独立 | 环境变量驱动 |
| **KPI / 指标定义** | ❌ **未独立** | Agent 规则（subtotal）与 Dashboard SQL（total_amount）两个真相源；无统一 Metric Registry |
| **数据时效契约** | ❌ **不存在** | as_of 只在 Dashboard；Agent 链路无数据截止日概念（P0-1 根因） |

**一句话结论：距离真正 Business Agent 还差「业务语义服务层」——统一指标定义（KPI Registry）、数据时效契约（as_of 贯穿全链路）、可解释/可拒绝契约。** 技术管道层（Agent Core/Adapter/Profile）在 Phase 13 已就位，本次审计证明短板不在管道而在语义。

## 14. 风险与诚实边界

1. **单模型结论**：所有 EX 数据基于当前运行模型 deepseek-chat（1 次运行，temperature=0 下仍存在服务端非确定性）。mimo-v2.5-pro 等其他模型未在 RBQ 上复测；冻结基准 90% 与本审计 59.1% **不可比**（题集/模型均不同）。
2. **样本量**：P20=22 题，1 题 = 4.5pp；分类结论（口径 4 题/时间 3 题）方向明确但精确比例有待 Pilot 真实问题分布修正。
3. **静态库偏差**：审计发现的时间漂移问题在「实时更新的真实库」上会缓解甚至消失——但当前产品形态（静态演示库）下它是现实风险；若 Pilot 换真实库需重建 Profile（Phase 13 已验证边际成本 ≈ 125 行配置）。
4. **gold 的主观性**：RBQ 的「业务口径」gold 由本阶段定义（如「本月=最新数据月」），已逐题在 business_rule 声明推理依据，但存在其他合理口径的可能（如把部分月的 9 月排除）；这正是口径必须产品化（P0-2）的原因。
5. **陷阱题判定含主观成分**：0/4 拒绝是明确事实；「编造」判定基于行为与库结构的客观比对（VIP 无字段、退款无字段、窗口漂移），但「理想行为」标准可讨论。
6. **UX 走查为静态代码审计**：未做真人可用性测试；评级基于代码证据与常规可用性准则，Pilot 观察将提供真人数据。
7. **本阶段零代码改造承诺**：git 状态复核——业务代码（backend/frontend/evaluation）零修改；新增仅审计工具 2 个脚本、数据集 1 个、产物 3 个、本报告。
